# Phase 11：长篇小说节奏 + 人机协作 + 角色群像 + 章节评价 综合方案

## 四大维度问题与方案总表

| 维度 | 问题 | 核心根因 | 方案 |
|---|---|---|---|
| **I 章节评价** | 每章评价结果被丢弃 | ReaderReviewAgent 评价了但不落库/不展示/不反馈 | **I：章节质量报告系统** |
| **H 角色群像** | 24 章仅 7 角色，关系不交错 | 初始硬编码 3 角色；关系边 0 条动态；升级门槛高 | **H：角色群像+关系网络** |
| **F 节奏** | 字数固定、剧情太快、无喘息章 | 四段式硬编码；plotting 强制每章推剧情 | **F：喘息章+字数动态化** |
| **G 人机编辑** | 只有整章重写 | 无段落级 API 和交互 | **G：局部改写扩充** |

## I：章节质量报告系统（新增 — 用户最新需求）

### 核心发现
ReaderReviewAgent **每章已在运行**（5 维度评分），但 ReviewReport 是纯内存对象——只触发自动重写就丢弃。用户看不到任何评价。

### I1：章节评价持久化

| 改动 | 文件 | 内容 |
|---|---|---|
| 新建 domain | `domain/ChapterReview.java` | 章节评价报告：chapterIndex + 5 维度评分(engagement/coherence/character/hook/overall) + summary + issues[] + improvement + createdAt |
| 新建表 | `SqliteSchemaInitializer` | `chapter_reviews` 表（id, project_id, chapter_index, scores_json, overall_score, summary, issues, improvement, created_at）|
| Repository | `SqliteNovelRepository` | +saveChapterReview / +findChapterReview(projectId, chapterIndex) / +findChapterReviewsByProject |
| NovelOrchestrator | runWritingOneChapter | 每章读者评审后调用 saveChapterReview 持久化 |

### I2：聚合章节质量报告

每章写完后的所有检测器输出（ReaderReview + ContinuityChecker + ConsistencyGuard + ConsistencyGate + SceneClassifier + 伏笔检测）聚合成一份**章节质量报告**。

| 改动 | 文件 | 内容 |
|---|---|---|
| 新建 domain | `domain/ChapterQualityReport.java` | 聚合报告：review(读者评分) + issues[](所有 ContinuityIssue) + sceneType + foreshadowingResolved + clicheCount |
| 新建 API | `ContentController` | `GET /chapters/{chapterIndex}/quality` 返回该章聚合质量报告 |
| NovelOrchestrator | 新建 `buildChapterQualityReport` | 每章写完后聚合所有检测结果 |

### I3：前端章节评价展示

| 改动 | 文件 | 内容 |
|---|---|---|
| 章节评价卡片 | `InteractiveReview.tsx` 或 `ChapterReader.tsx` | 每章展示：5 维度雷达图/评分条 + 问题列表 + 改进建议 + 检测器输出 |
| API 调用 | `client.ts` | +getChapterQuality(id, chapterIndex) |

### I4：评价反馈到下一章

| 改动 | 文件 | 内容 |
|---|---|---|
| 逐章反馈注入 | `ContextAssembler.buildFeedbackSection()` | 读取上一章的 ChapterReview，把 issues + improvement 注入下一章写作上下文 |
| 低分预警 | `NovelOrchestrator` | 连续 2 章 overall < 7 → 暂停写作 + 在界面提示人工介入 |

## H：角色群像与关系网络

### H1：角色群像规划（初始角色从 3 个→按篇幅动态）
- `NovelOrchestrator.runConceiving()`：根据预计总章数计算角色数（每 3-4 章 ≥1 个有名角色），批量设计
- `GenreRuleProvider.getCharacterEnsembleSpec()`：题材化角色结构（权谋：1主角+2对手+3盟友+2中间派+2情感线）
- `plotting.st`：要求每卷引入 2-3 个新配角 + 设计与已有角色的关系

### H2：角色升级增强（让 5 个未升级实体快速升级）
- `CharacterProfileUpgrader`：spanThreshold 2→1，补全智谋建模字段
- `NovelOrchestrator`：每卷结束时批量扫描升级"有名字但无档案"的实体

### H3：关系网络动态化（60 条边从全静态→真正演变）
- 新建 `agent/RelationshipEvolutionTracker.java`：每章 LLM 检测关系变化（敌变友/背叛/结盟）
- 新建 `prompts/relationship-evolution.st`
- `EntityGraphService`：收到变化事件后 expire 旧边+插入新边
- `EntityGraphService` 召回窗口 5→8 章，上限 25→40

### H4：关系网络注入写作
- `ContextAssembler.buildRelationshipWeb()`：注入本章出场角色之间的当前关系
- `chapter-writing.st`：新增"展现角色关系张力"指令

## F：节奏自适应

### F1：喘息章机制
- `ChapterSynopsis` +chapterType（CLIMAX/BREATHING/DEVELOPMENT/TRANSITION）
- `plotting.st` 允许喘息章（每卷 1-2 章不推进主线，tension≤3）
- `GenreRuleProvider` +getChaptersPerVolume（权谋 10-15 章/卷）
- `ContextAssembler` 按 chapterType 差异化字数/结构/爽点约束

### F2：字数动态化
- `WritingPreferences` +maxChapterLength(6000) +chapterLengthVariation(VARIED)
- `chapter-writing.st` 四段式字数→`{{chapterLengthGuide}}` 动态注入
- `ChapterWriterAgent` maxTokens 3000→4000

### F3：节奏过快检测
- `PlotProgressionDetector` +连续 4 章张力≥6 → "建议喘息章"
- `WritingPreferences` +fastPaceWindow(4)

## 实现顺序

| Step | 方案 | 优先级 | 依赖 |
|:-:|---|:-:|---|
| 1 | **I1-I2 章节评价持久化+聚合** | 🔴 最高 | 无（用户最关心，最快见效）|
| 2 | **I3-I4 评价展示+反馈** | 🔴 最高 | I1 |
| 3 | **H1 角色群像规划** | 🟠 高 | 无 |
| 4 | **H2 角色升级增强** | 🟠 高 | H1 |
| 5 | **H3-H4 关系网络动态化+注入** | 🟠 高 | H1 |
| 6 | **F1 喘息章机制** | 🟡 中 | 无 |
| 7 | **F2-F3 字数动态化+过快检测** | 🟡 中 | F1 |

## 题材无关性
全部方案为通用机制：评价维度（吸引力/连贯/角色/钩子）适用所有题材；角色结构（主角/对手/盟友/中间派）通用；喘息章概念通用；段落编辑是纯文本操作。
