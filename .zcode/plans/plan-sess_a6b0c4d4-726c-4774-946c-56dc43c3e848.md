# 百万字可靠性修复方案：完整设计（10 个差距 → 4 个阶段 → 15 个 feature）

> 基于 3 轮 Explore agent 对全部子系统的代码级审查。每个 feature 含根因、修复、验收、影响文件。按依赖排序为 4 阶段。

---

## Phase A — 安全地基（3 feature，无依赖，快速止血）

### A1. 质量门禁 fail-closed（差距 #4）
- **根因**：`NovelOrchestrator.runFinalAuditGate` catch Exception → return true（`NovelOrchestrator.java:1427`），门禁代码异常时静默放行劣质书
- **修复**：catch 块改为 `log.error + return false`（fail-closed）；增加测试验证异常时不 PASS
- **验收**：`mvn test -Dtest=FinalAuditGateFailClosedTest`
- **文件**：`NovelOrchestrator.java`、`FinalAuditGateTest.java`

### A2. PRAGMA 每连接修复（差距 #6）
- **根因**：`ConnectionProvider.java:14` 的 `pragmasInitialized` 标志导致 foreign_keys/busy_timeout/synchronous 仅应用到第一个连接；后续所有连接默认值（FK OFF, busy_timeout 0）
- **修复**：`getConnection()` 中 `journal_mode=WAL` 保留 once-only（持久化），`foreign_keys=ON`/`busy_timeout=5000`/`synchronous=NORMAL` 改为每连接执行
- **验收**：`mvn test -Dtest=ConnectionProviderPragmaTest`
- **文件**：`ConnectionProvider.java`

### A3. 去重 style-guardian 调用（差距 #10）
- **根因**：`NovelOrchestrator.java:856-873`（log 后丢弃）和 `916-945`（持久化 issue）每 5 章各调一次 `styleGuardian.checkConsistency`——前者输出被丢弃，纯浪费 LLM 调用
- **修复**：删除 856-873 块（只做 log），保留 916-945（含评分+持久化）；如需 baseline 格式合并到后者
- **验收**：`mvn test`（现有测试不回归）
- **文件**：`NovelOrchestrator.java`

## Phase B — 数据完整性（2 feature，百万字基础）

### B1. 章节写入事务（差距 #1）
- **根因**：全局零事务，saveChapter + saveSummary + saveEntities + saveForeshadowings 各自独立连接独立提交，中途失败残留不一致状态
- **修复**（Design A — connection-passing，匹配现有 `saveVolume(Connection)` 模式）：
  - `SqliteNovelRepository` 新增 `<T> T runInTransaction(Function<Connection, T> work)`：`setAutoCommit(false)` → 执行 → `commit()`/`rollback()`
  - 新增 connection-accepting 重载：`saveChapter(Connection,...)`、`saveSummary(Connection,...)`、`saveContinuityIssue(Connection,...)`
  - `NovelOrchestrator.doWriteOneChapter` 核心保存段（saveChapter + saveContinuityIssue + saveChapterReview）包入一个事务
  - **范围控制**：仅包"核心章节数据"（chapter + review + continuity issues），不包 agent 内部的 entity/foreshadowing 提取（那些在 fault-isolated try/catch 中，保持独立）
- **验收**：`mvn test -Dtest=ChapterTransactionTest`（模拟中途抛错断言整体回滚）
- **文件**：`SqliteNovelRepository.java`、`NovelOrchestrator.java`

### B2. 分页加载消除 OOM（差距 #2）
- **根因**：`findChaptersByProject` 加载全部章节正文到堆；`findRecentChapters` 先加载全部再截取子列表——400 章约 120 万字一次性入堆
- **修复**：
  - `SqliteNovelRepository.findRecentChapters` 改为 `ORDER BY chapter_index DESC LIMIT ?`（零调用方改动）
  - `NovelRepository` 新增 `int countChaptersByProject(projectId)`（替代 `.size()`）
  - `NovelRepository` 新增 `List<Chapter> findChaptersByIndexRange(projectId, from, to)`
  - `NovelOrchestrator.updateStyleProfile`（:745）改用 `findChaptersByIndexRange(toChapter-4, toChapter)`
  - `ForeshadowingImportanceAuditor`（:159）改用 `countChaptersByProject`
  - `QualityEvaluationAgent`（:161）改用按索引取 3 章（首/中/末）
- **验收**：`mvn test -Dtest=ChapterPaginationTest`
- **文件**：`NovelRepository.java`、`SqliteNovelRepository.java`、`TestNovelRepositoryStub.java`、`NovelOrchestrator.java`、`ForeshadowingImportanceAuditor.java`、`QualityEvaluationAgent.java`

## Phase C — 长程记忆（4 feature，打通 30-100 章）

### C1. master outline 演进 + 卷结构对齐（差距 #3）
- **根因**：`outline.premise` 写一次永不更新；`PlotterAgent:123` 规划 20 章/卷但 `NovelOrchestrator:1479` 硬编码 8 章/卷——master 的卷弧线与实际生成的卷完全错位
- **修复**：
  - **对齐**：`master-outline.st` 模板"15-30 章/卷"→"约8章/卷"；`PlotterAgent:123` volumeCount 改为 `totalChapters / 8`
  - **演进**：`generateVolumeSummary` 尾部（:686 后）追加逻辑——从卷级 Summary 重建"【已写卷摘要】"段写入 `outline.premise`（每卷一行，超过 10 卷时早期卷合并为"前N卷"一行）；保存 outline
  - **planVolume 上下文增强**：`tryExtendLayeredOutline` 的 `previousSummary` 从"最后一条记录"改为"最近 2-3 个卷级摘要拼接"，按 fromChapter 排序
- **验收**：`mvn test -Dtest=MasterOutlineEvolutionTest`（卷末后 premise 含已写卷摘要；planVolume 收到聚合前文）
- **文件**：`master-outline.st`、`PlotterAgent.java`、`NovelOrchestrator.java`

### C2. 全书摘要层修复记忆地平线（差距 #5）
- **根因**：`VOLUME_DETAIL_LIMIT=3` + 更早卷截断 100 字→第 24 章后模型对前文基本失忆
- **修复**（Design 3B — projects 新列，最低爆破半径）：
  - `projects` 表加列 `book_summary TEXT`（migration）
  - `generateVolumeSummary` 尾部：用"上一版全书摘要 + 本卷摘要"调 LLM 重新压缩为 ≤3 句全书摘要，存入 `project.book_summary`
  - `ContextAssembler.buildRecentSummary` 最顶部注入全书摘要（全文，不受 VOLUME_DETAIL_LIMIT 裁剪）
  - 旧卷 100 字截断放宽到 300 字（保留首句而非前 100 字）
- **验收**：`mvn test -Dtest=BookSummaryHorizonTest`（全书摘要注入；100 章后仍有全书摘要）
- **文件**：`SqliteSchemaInitializer.java`、`SqliteNovelRepository.java`、`NovelOrchestrator.java`、`ContextAssembler.java`、`Project.java`

### C3. outline N+1 查询消除 + ContextAssembler 缓存（差距 #7）
- **根因**：`findOutlineByProject` = 2+N 次查询（N=卷数）；`ContextAssembler.assemble` 单次调用加载 outline 3 次→1 章 6+3N 次查询
- **修复**：
  - `findOutlineByProject` 重构为 3 次查询（1 outline + 1 volumes + 1 JOIN synopses），内存分组
  - `ContextAssembler.assemble` 顶部加载 outline 一次，传递给 `buildPremiseSection`/`buildVolumeOutline`/`findFullSynopsis`
  - `saveOutline` 改用单连接（修复 :314-327 的两连接 latent bug）
- **验收**：`mvn test -Dtest=OutlineQueryCountTest`（查 outline 的 SQL 次数恒定 3 次）
- **文件**：`SqliteNovelRepository.java`、`ContextAssembler.java`

## Phase D — 成本与性能（3 feature，影响速度/费用）

### D1. ContextAssembler 稳定段缓存（差距 #8 部分）
- **根因**：6 个稳定 section（premise/style/worldbuilding/characterVoice/knowledgeQuotes/narrativeThread）每章重新 DB 查询 + 字符串拼接
- **修复**：
  - `ContextAssembler` 加 `Map<String, String> stableSectionCache`（key=projectId+sectionName）
  - 6 个稳定 builder 加缓存；失效条件：saveStyleProfile/saveOutline/saveKnowledgeEntry/saveEntityEdge 时清除对应 key
  - **不做** gateway 级缓存（chapter-writing prompt 每章变化，gateway 缓存无收益且高风险）
- **验收**：`mvn test -Dtest=StableSectionCacheTest`（同一项目第二次 assemble 不重复查 DB）
- **文件**：`ContextAssembler.java`

### D2. embedding 批量化 + 向量库增量持久化（差距 #8+#9）
- **根因**：`CloudApiEmbeddingProvider.embed` 每文本 1 次 HTTP 调用（~5-8 次/章可批量化为 1 次）；`EmbeddedVectorStore.persist` 每次全量序列化
- **修复**：
  - `EmbeddingProvider` SPI 加 `List<float[]> embedBatch(List<String> texts)`
  - `CloudApiEmbeddingProvider.embedBatch`：`"input": [array]`，按 response `index` 字段排序返回
  - `VectorRetrievalService.indexBatch(List<IndexedText>)`：一次 embed + 批量 upsert
  - `ChapterWriterAgent.indexChapterInChunks`：收集 chunks → 一次 `indexBatch`（~5-8 调用 → 1）
  - `EmbeddedVectorStore`：预计算 L2 归一化向量（cosine 简化为 dot product）+ per-project 二级 Map（避免跨项目遍历）
  - 增量持久化：append-only log 替代全量 ObjectOutputStream（周期性 compact）
- **验收**：`mvn test -Dtest=EmbeddingBatchTest`、`mvn test -Dtest=VectorStoreScalingTest`
- **文件**：`EmbeddingProvider.java`、`CloudApiEmbeddingProvider.java`、`StubEmbeddingProvider.java`、`VectorRetrievalService.java`、`ChapterWriterAgent.java`、`EmbeddedVectorStore.java`

### D3. 向量库搜索优化（差距 #9，可选进阶）
- **根因**：O(N) 暴力 cosine 搜索
- **修复**：如 D2 的 L2 归一化 + per-project Map 不足以满足延迟，引入 JVector（纯 Java ANN，无 native 依赖）替换 EmbeddedVectorStore 的 search 实现（VectorStore SPI 不变）
- **验收**：`mvn test -Dtest=VectorStoreScalingTest`（2000 向量搜索 < 50ms）
- **文件**：`pom.xml`、`EmbeddedVectorStore.java`（或新 JVectorVectorStore）
- **优先级**：仅当 D2 后延迟仍不可接受时启动

## 实施顺序与依赖

```
Phase A（并行，无依赖）
  A1 门禁 fail-closed ─┐
  A2 PRAGMA 修复     ──┼── 提交 → 验证
  A3 去重 style-guard ─┘

Phase B（A 完成后）
  B1 事务 ────────────── 提交 → 验证
  B2 分页加载 ────────── 提交 → 验证

Phase C（B 完成后，C1/C2/C3 可并行）
  C1 master 演进 ─┐
  C2 全书摘要    ──┼── 提交 → 10 章 e2e 验证
  C3 N+1 消除    ─┘

Phase D（C 完成后）
  D1 稳定段缓存 ──┐
  D2 批量+增量   ──┼── 提交 → 成本对比
  D3 ANN（可选） ─┘
```

## 验收里程碑

| 阶段 | 验证 | 目标 |
|---|---|---|
| Phase A | `mvn test` | 全绿 + fail-closed 测试 |
| Phase B | `mvn test` + 10 章 e2e | 事务回滚 + 分页无 OOM |
| Phase C | 10 章 e2e + 质量评估 | consistency 不降、记忆地平线扩展 |
| Phase D | 10 章 e2e + 成本对比 | embedding 调用 -80%、向量搜索延迟可接受 |
| 最终 | 30 章 e2e + 质量评估 | overallScore ≥ 8、0 失败、≈10 万字 |

## 规模预估

- 每个 feature：1-3 文件改动、1 个测试、可独立验证
- 总计：15 feature × ~2 文件 = ~30 文件改动 + ~12 新测试
- 不改 prompt 模板变量名（仅 master-outline.st 的"15-30章"→"约8章"文本调整）
- 数据库 migration：2 列（book_summary、现有 cast/beats/climax 已在）
