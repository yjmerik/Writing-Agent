# 《听雪刀》武侠长篇 UI 全流程体验报告

日期：2026-09-23 至 09-24。方法：ego-browser 驱动真实浏览器，以作者身份走完「新建项目 → 构思审阅修改 → 逐章生成与审阅 → 终局 → 成书门禁」全流程；全部内容为真实 LLM 生成（qwen3.8-flash，百炼 Token Plan），未使用回放或直调业务 API 代替界面操作（诊断性 API 调用仅用于读取状态与定位缺陷，均已在文中标注）。

## 一、旅程概览

| 阶段 | 结果 |

| 新建项目 | 《听雪刀》，武侠预设，目标 24 章，每章审阅 |
| 构思（约 17 分钟） | 世界观+8 人物卡+总纲+3 卷章纲+9 条伏笔+真典 8 条，质量高 |

最终成书规模：18 章（正文 10 + 尾声回收 8），70,260 字，全部逐章作者批准。

## 二、单章生产管线实测

以第一章为例（含一次 quality_council 自动重写）：
写作 121s → 连续性检查 441s → 质量评审（8/10 通过）→ 重写 215s → 连续性复查 522s → 质量复查 → 暂停待人审。
- 无重写章节约 12-15 分钟；有重写或补查约 25-40 分钟。
- 每章质量评分 7-8/10，文风稳定（账/刀/雪意象系统、高对话密度、短句白描），人物口癖一致。
- 自动纠偏复验（correction-verification）在第 6、8 章正常工作，能逐条确认修复（含"问式未成"这类能力边界修复）。

## 三、作者工作流验证（本轮新证）

1. **手动编辑可靠**：第一章作者改「火漆→蜡封」（7 处）、「涉嫌」句改写，保存为 v4，刷新逐字核对无丢失。对比 0905 报告的"作者保存被覆盖"已修复。
2. **定向 AI 修订有效**：第三章「封口药用错对象+虎口旧疤写成左腕」两条 HIGH，用修改意见重写给出定位后，v3 逐字落实（含韩照骨"未验。验过才算数"的隐瞒戏落地）；第五章拓痕无获取链同样一句话修复。0905 报告"修订不落实"未复现。
3. **计划偏离对照、影响预览、卷末回读、整书记录校验报告**等作者工具内容质量高、诚实标注缺口。
4. **裁决台账（处置）**：作为过期 HIGH 的正常出口，NCS-071 流程可用；批准门禁按台账豁免生效。
5. **幂等重试（NCS-075）**：WORKER_FINALIZING 冲突下同一幂等键重发最终成功，返回原结果。

## 四、缺陷与结构性问题（按严重度）

### P1-1 「重新检查」按钮是装饰，未查清项无 UI 出路（本轮最大死锁）
- 位置：`frontend/src/components/ReviewClassificationView.tsx:63`，UNKNOWN_CHECK 类条目的按钮**没有 onClick**。
- 后果：correction-verification/consistency-guard 失败后留下「未查清」检查点，批准 API 永远 409；「补查当前稿连续性」只重跑连续性，不清该检查点（服务端消息明示"其他报告仍按各自稿号显示"）。第一章因此卡死，最终靠「作为创作例外保留」裁决旁路。
- 复验标准：UNKNOWN_CHECK 条目点击后应触发 `/chapters/{n}/recheck` 并在完成后更新检查点。

### P1-2 批准 409 对作者近乎不可见
- 服务端 409（未解决 HIGH/WORKER_FINALIZING/REVIEW_CONFLICT）发生时，前端只有一闪而过的 message warning（默认 3 秒）或完全无反馈；按钮禁用态（identity 与正文版本不一致时）仅有 hover tooltip，视觉无差异。
- 实测同一位置点击 4 次无任何反馈，作者无法得知"为什么批不了、差什么"。建议：409 原因常驻显示在审核卡；禁用按钮给出静态视觉与文字说明。

### P1-3 延迟生成的末章按旧 24 章结构规划成"新篇开头"
- 卷4 计划到第 9 章，第 10 章标"延迟生成"。实际生成时按含第 14、22 章回收位的旧结构规划出「雪盐引子」（卷2 开篇），导致 10 章的书没有终局，且埋下 39 条新候选线索。
- 作者不得不手写终局指令重写（「让 Agent 修改」+ 明确六点结局要求，结果良好）。延迟生成的章纲应继承压缩后的目标与剩余章数约束。

### P1-4 伏笔承诺通胀 vs 篇幅压缩：尾声回收卷被触发
- 压缩到 10 章后，各章仍持续新埋伏笔（第 10 章一稿即 39 条候选线索），账本累计 108 条、未回收最高 71 条。
- 成书门禁伏笔审计将 16 条升级 HIGH、判定 62 条必须回收，**自动追加第 11-18 章尾声回收卷**，章名即「第N章·伏笔回收」。
- 影响：a) 书被系统自动加长；b) 回收章文学价值明显低于正文；c) 逐章批准成本大。作者最终以台账结清（resolve API）+批准已完成章收尾。
- 建议：压缩篇幅时同步收缩承诺账本；候选线索默认不进入"必须回收"；尾声回收卷需要作者确认而非自动追加。

### P2-1 每次保存新版本，旧报告全部过期并继续阻塞
- 「保存/应用修改后会自动触发重新检查」实际未发生（手动编辑后 reportCurrent 仍绑旧稿号）；过期 HIGH 持续 409 阻塞批准，只能逐条人工裁决。第一章 4 条→9 条→17 条过期检查的滚雪球过程均有截图证据。
- 建议：新版本落库时自动重跑受影响检查，或将过期问题在批准门禁中降级为提示。

### P2-2 状态与文案残留误导
- 「请先处理待审核内容，再继续创作」横幅在无任何待审项时长期残留（多次复现），配合「写作受阻」chip 出现在已可继续的状态；审核卡摘要（预览正文）不随新版本刷新。
- 「协作写作进行中」chip 在章节已暂停待人审时仍显示，导致轮询判断失真。

### P2-3 弹窗/抽屉残影与不关闭
- 「修改意见」弹窗提交成功后不自动关闭（多次复现）；抽屉塌缩后留下 width=0 的遮罩层拦截点击（需整页刷新）；「篇幅与计划」每次点「影响预览」会**重置全部已填处置**（连续点两次预览即丢失全部选择），且 MIGRATE 必须填目标章号这一点无明显提示。

### P2-4 遥测归属缺失
- 修订管线（修改意见重写、让 Agent 修改）触发的 LLM 调用 projectId 为空，事件日志无法按项目归集成本；STRUCTURED_OUTPUT_RETRY 显示抽取器曾输出非 JSON 被重试（韧性正常）。

### 头条发现：状态机无法到达 FINAL（P0 级结构性死锁）
完结的唯一路径是「大纲耗尽 → 无必须回收伏笔 → finishBookWithGate」。但：
1. 每写完一卷，**总纲中段重规划自动追加下一卷**（卷6=第 19-26 章），不受 `targetChapters=10` 约束，也不管书是否已完结——内容生成无上界；
2. 回收章自身继续埋设新伏笔（尾声 8 章新增 31 条承诺），即使作者实时结清，门禁审计仍在消耗后再次触发追加；
3. 作者的正规出口全部失效：大纲删除不持久化（草稿保存静默失败）；大纲 PUT 被「已写章节及所属卷不可修改」+「章号必须严格递增」双重校验挡死（历史卷序混乱：卷1[1]→卷2[10]→卷4[2-9]）；拒绝卷6大纲并指示「不要生成后续卷」时，Plotter 返回空大纲被系统当作错误（409「Plotter 返回空卷大纲候选」）——**系统无法表达"没有更多内容"**。
4. 结果：18 章完整小说无法通过产品流程进入「已完结」，只能停留在检查点暂停。系统自检（剧情停滞警告：连续 3 章未明确剧情目的）已确认尾声章在漂移，但机制仍强制续写。

建议：a) 中段重规划与大纲延展必须尊重 targetChapters 与"账本清零+全书完结意图"；b) 提供「作者宣告完结」入口（直接触发行成书门禁）；c) 空大纲候选应被视为合法的"全书完"信号。
