## J1：字数硬约束

### 根因
`WritingPreferences.maxChapterLength`(默认6000)是死代码——全代码库无任何业务逻辑读取它。`chapterLengthGuide` prompt 上限 5500 过高。`rewriteForCorrection` 下限仅 500、无上限校验。

### 方案

**① 激活 maxChapterLength 约束**

| 改动 | 文件 | 内容 |
|---|---|---|
| buildChapterLengthGuide | `ChapterWriterAgent.java` | 从 prefs 读取 maxChapterLength，生成"本章字数不超过 X 字"的硬约束指导。长章分支从 4000-5500 改为 3500-4500（符合网文标准） |
| buildWritingConstraints | `ContextAssembler.java` | 新增 maxChapterLength 约束注入："□ 本章正文不超过 {maxChapterLength} 字。超过此限请精简次要场景" |
| rewriteForCorrection 下限 | `ChapterWriterAgent.java:200` | 下限 500→minChapterLength（与 write() 一致） |
| 写后字数上限校验 | `ChapterWriterAgent.java` write()/rewriteForCorrection() | 写后如果 > maxChapterLength，log.warn 但不截断（LLM 无法精确控制字数，靠 prompt 约束 + 后续分段编辑） |

**② chapter-writing.st 字数指导修正**

| 改动 | 文件 | 内容 |
|---|---|---|
| 字数指导 | `chapter-writing.st` | 四段式字数指导中加入"总字数控制在 {targetRange} 字。宁可精简也不要注水" |

## J2：桥段追踪 + 重复检测

### 根因
GenerationLog.keyElements 恒为"[]"（3处硬编码），CreativeDiversityService 不追踪章节正文桥段，无语义级重复检测。

### 方案

**① 修复 keyElements 硬编码**

| 改动 | 文件 | 内容 |
|---|---|---|
| 填充 keyElements | `NovelOrchestrator.java:176/225/265` | 3处 `"[]""` 改为传入实际关键元素 JSON 数组（如 `["维度:政治","维度:经济"]`） |

**② 新建桥段追踪器**

| 改动 | 文件 | 内容 |
|---|---|---|
| 新建 agent | `agent/PlotMotifTracker.java` | 每章写完后用 LLM 提取本章的"叙事桥段标签"（如"告别送行""公堂对峙""暗夜刺杀""宴席博弈"），记录到 GenerationLog |
| 新建模板 | `prompts/plot-motif-extract.st` | 输入章节正文 → 输出 1-3 个桥段标签 |
| 重复检测 | `PlotMotifTracker` | 查询最近 N 章的桥段标签，如果与本章标签重复→ContinuityIssue(STRUCTURE, MEDIUM)："本章桥段'{label}'与第X章重复" |
| 注入约束 | `ContextAssembler.buildWritingConstraints()` | 注入"最近章节已使用的桥段：{list}，本章应避免重复" |

**题材无关性**：桥段标签由 LLM 根据正文自由提取，不预设任何题材特定的桥段清单。

## J3：伏笔悬置告警

### 根因
无间隔提醒机制；isOverdue 依赖 expectedResolveChapter 但动态伏笔不设此字段；逐章无悬置告警。

### 方案

| 改动 | 文件 | 内容 |
|---|---|---|
| 悬置阈值 | `WritingPreferences.java` | +`foreshadowSuspenseThreshold`(默认 8)：伏笔悬置超过 N 章未回收→告警 |
| 逐章告警 | `NovelOrchestrator.runWritingOneChapter()` 写后 | 检测所有未回收伏笔的 suspenseChapters，> threshold 的→ContinuityIssue(FORESHADOWING, MEDIUM)："伏笔'{desc}'已悬置{N}章（埋于第X章），建议在近期章节回收" |
| isOverdue 改进 | `Foreshadowing.java` | 新增 `isStale(int currentChapter, int threshold)` 方法——不依赖 expectedResolveChapter，只看悬置章节数 |
| 间隔提醒 | `ContextAssembler.buildForeshadowings()` | 悬置超过 threshold/2 的 MEDIUM 伏笔，也加入"⚠️ 即将过期"提醒段（即使不在 top LIMIT 内） |

## J4：说明文密度检测

### 根因
prompt 无诏书口语化指令；无连续说明性文本检测器。

### 方案

**① prompt 增强**

| 改动 | 文件 | 内容 |
|---|---|---|
| 诏书口语化 | `chapter-writing.st` | 写作质量要求新增："诏书/疏文/条文/规章不要原文念诵——用角色对答、简述、旁观者反应来传递关键信息。如必须引用原文，只引核心一句，其余用'大意是...'概括" |

**② 说明文密度检测（纯规则）**

| 改动 | 文件 | 内容 |
|---|---|---|
| 新建检测器 | `service/ExpositionDetector.java` | 纯规则：统计连续段落中无对话（无引号）的段落比例。如果连续 5+ 段无对话→ContinuityIssue(PACING, MEDIUM)："本章连续{N}段无对话，大段说明性文本影响阅读节奏。建议插入角色反应或对话打断" |
| 接入 | `NovelOrchestrator.checkContinuityAfterWriting()` | 写后调用 |

## J5：动作戏质量增强

### 根因
HISTORICAL 规则无动作质量指导；chapter-writing.st 无动作描写质量指令。

### 方案

**① GenreRuleProvider 动作质量指导**

| 改动 | 文件 | 内容 |
|---|---|---|
| 动作质量规则 | `GenreRuleProvider.getChapterWritingRules()` | HISTORICAL 追加："动作/战斗场景要调动多感官（视觉/听觉/触觉），写出打击感、空间感和受伤反馈，不要流水账式叙述" |
| 题材化 | 同上 | 不同题材有不同的动作指导（武侠强调招式细节，悬疑强调紧张感，言情强调身体语言） |

**② chapter-writing.st 动作质量指令**

| 改动 | 文件 | 内容 |
|---|---|---|
| 动作描写 | `chapter-writing.st` | 写作质量要求新增："动作/战斗场景要有物理质感——调动视觉（光影/空间）、听觉（声响/呼吸）、触觉（疼痛/温度），写出打击感和身体反馈，不要'他一拳打过去对方倒地'式的流水账" |

## 实现顺序（按 harness 规范拆分特性）

| Feature | 方案 | 改动量 | 依赖 |
|:-:|---|---|---|
| **F-1** | J1 字数硬约束 | 3文件改 | 无 |
| **F-2** | J2 桥段追踪+重复检测 | 2新文件+2改文件 | 无 |
| **F-3** | J3 伏笔悬置告警 | 3文件改 | 无 |
| **F-4** | J4 说明文密度检测 | 1新文件+2文件改 | 无 |
| **F-5** | J5 动作戏质量增强 | 2文件改 | 无 |

每个 Feature 完成后：mvn compile + mvn test 通过 + 提交。

## 题材无关性
- 桥段标签由 LLM 自由提取（不预设清单）
- 伏笔悬置阈值可配
- 说明文密度检测是通用规则（无对话=说明性文本）
- 动作质量指导通过 GenreRuleProvider 题材化
