## 二、五大通用子系统设计

### A. 角色生命力系统（解决 #1 反派降智 / #2 配角扁平 / #7 能力漂移）

#### A1：对手智谋建模 — CharacterDesign 增强

**根因**：`character-design.st` 字段全是静态标签（"冷面对抗"），没有"对手应如何独立判断、反制主角"的结构化描述。

**方案**：扩展角色设计字段，加入"智谋模型"维度（通用，不针对权谋题材）。

- 扩展设计字段 `character-design.st`：新增 `【智谋层级】`(1-5)、`【反制能力】`(该角色面对主角策略时的典型反制手段 2-3 种)、`【独立判断原则】`(妥协/绝不退让的明确条件)、`【盲区】`(认知盲点)
- `Character.java` 新增字段 `strategyLevel`(int)、`countermeasures`(String)、`independentWill`(String)、`blindSpot`(String) + DDL 加列
- `chapter-writing.st` 新增铁律："**对手享有独立判断权**——每个有【反制能力】设定的角色，面对主角策略时至少执行一次反制动作（质疑/拖延/设反局/试探），不得因主角一句话就交底、退场或破防。"
- `WritingContext.java` 渲染角色时输出"■ 反制能力 / ■ 盲区"

**题材无关性**：`strategyLevel` 对所有题材适用——武侠里是"武功招式反制"，言情里是"情感防线反制"，科幻里是"技术反制"。`countermeasures` 是自由文本，由 GenreRuleProvider 提供题材化示例。

#### A2：角色弧光调度 — ArcScheduler（替换 ArcUpdater 被动模式）

**根因**：`ArcUpdater` 每 10 章事后重估，且冷场配角（10 章未出现）永久停滞。

**方案**：把"事后重估"改为"事前规划 + 出场调度"。

新建 `service/ArcScheduler.java`，每章写作前运行：
1. 查询所有角色的"上次出场章节"和"弧光当前阶段"
2. 识别"该出场但久未出场"的配角（基于 characterUpgradeSpan）
3. 识别"弧光停滞超过 N 章"的角色
4. 输出【本章角色出场建议】：建议本章让哪些配角出场 + 推进他们的弧光到下一阶段
5. 注入 ContextAssembler → chapter-writing.st 的 cast 指令

- `Character.java` 新增 `arcStage` 字段（弧光当前阶段文本，如"蛰伏→觉醒→考验→蜕变→完成"）
- `ContextAssembler.buildTaskSection()` 把 ArcScheduler 建议注入 cast 指令
- `ArcUpdater.java` 改为每章轻量更新 arcStage，而非每 10 章重写全文

#### A3：能力边界守卫 — AbilityGuard

**根因**：`Character.ability` 写一次后从不校验。

新建 `agent/AbilityGuard.java`，每章写完后用 LLM 检测："主角展现的能力是否超出 ability 设定？"（如设定"不习武"但本章"翻屋顶/拔剑格挡"）→ 越界则 `ContinuityIssue(CHARACTER, HIGH)` 触发重写。
- 新建 `prompts/ability-check.st`
- `chapter-writing.st` 铁律："角色行为不得超出其【能力】设定；能力成长必须有跨章铺垫。"

### B. 节奏与结构多样性系统（解决 #3 信息过载 / #4 结构套路化）

#### B1：信息密度调控 — DensityController

**根因**：系统完全不存在"每章事件数量"的度量；`ContextAssembler:425` 只要求"覆盖节拍"不设上限。

新建度量 + 上限调控：
- 写前（大纲层）：Plotter 生成大纲时要求每章标注 beatCount；`> maxBeatsPerChapter`(默认 4) → 警告
- 写后（正文层）：LLM 检测正文实际事件数 vs 大纲节拍数偏差
- 连续 2 章密度过载 → 建议下一章设为"过渡章"（beatCount ≤ 2）

改动：
- `ContinuityIssue.Type` 新增 `DENSITY`、`STRUCTURE` 枚举值
- `WritingPreferences.java` 新增 `maxBeatsPerChapter`(默认 4)、`transitionChapterInterval`(默认 5)
- `ContextAssembler.buildWritingConstraints()` 注入"本章核心事件不超过 N 件"
- `PlotProgressionDetector` 扩展密度维度

#### B2：场景结构多样性引擎 — 激活死代码 + 场景分类

**根因**：`DiversityTracker.record()` 从未被调用（死代码）；无"场景结构类型"概念。

新建 `domain/SceneType.java`（7 种题材无关的抽象场景类型）：CONFRONTATION(对抗/博弈)、ACTION(行动/追逐/战斗)、INVESTIGATION(调查/推理)、EMOTIONAL(情感/关系)、REVELATION(揭示/转折)、TRANSITION(过渡/铺垫)、CEREMONY(仪式/盛典)

新建 `agent/SceneClassifier.java`，每章写完后用 LLM 把章节归类为一种 SceneType，写入 DiversityTracker 的 scene 维度。连续 3 章同一 SceneType → `ContinuityIssue(STRUCTURE, MEDIUM)`。

改动：
- 激活 `DiversityTracker.record()`（当前死代码）—— `NovelOrchestrator.runWritingOneChapter()` 每章写完后调用三个维度
- `DiversityTracker.java` 新增 scene 维度
- `GenreRuleProvider.java` 每题材提供"推荐 SceneType 分布"（武侠 ACTION 高、言情 EMOTIONAL 高、权谋 CONFRONTATION 高）

**为什么题材无关**：SceneType 是 7 种抽象叙事功能，任何题材的小说都由这些功能组合而成。

### C. 因果完整性系统（解决 #5 伏笔遗忘 / #6 金手指）

#### C1：伏笔全生命周期闭环 — 从"被动记账"到"主动规划 + 强制回收"

**根因链**（四重失效）：A. 无 priority/deadline；B. 注入 top 8 按埋设章倒序（旧伏笔被挤出）；C. 检测器只读前 2000 字；D. FINAL 门禁不阻塞。

**五环闭环**：埋设 → 标记重要性 → 规划回收 → 强制注入 → 检测回收 → 门禁阻塞

① **数据模型增强**：`Foreshadowing.java` 加 `priority`(HIGH/MEDIUM/LOW)、`expectedResolveChapter`、`mustResolve`(boolean)；DDL 加列；Repository 加 priority 排序和 deadline 过滤

② **大纲层规划**：`plotting.st` 新增"伏笔规划"段（每条伏笔标注 [重要性H/M/L]、[埋设章]、[预计回收章]）；`ChapterSynopsis.java` 加 `foreshadowingsToPlant`、`foreshadowingsToResolve`

③ **提取标记重要性**：`foreshadowing-extract.st` 输出格式增加 priority 字段

④ **上下文注入改革**：`ContextAssembler.buildForeshadowings()` 改排序策略——HIGH+mustResolve 永不裁剪，其余按"挂得最久"降序；`chapter-writing.st` 新增 `mustResolveSection` 条件块强制回收指令

⑤ **检测器修复**：删除 `ForeshadowingResolutionDetector:47` 前 2000 字截断（分段检测全文）；改进 `:91` 6 字模糊匹配为语义匹配

⑥ **FINAL 真门禁**：`NovelOrchestrator.runWritingLoop()` L775-788 改为——HIGH priority 且 mustResolve=true 未回收 → 不转 FINAL，注入回收指令继续写（最多追加 3 章防无限循环）

#### C2：因果链守卫 — CausalityGuard

**根因**：无"证据/道具须有合法来源"的约束。

新建 `agent/CausalityGuard.java`，每章写完后 LLM 检测："主角使用的关键证据/道具/信息，在前文是否有获取场景或铺垫？"凭空出现 → `ContinuityIssue(PLOT, HIGH)`。维护"已获取道具/信息"清单（从实体图谱查询）。
- 新建 `prompts/causality-check.st`
- `chapter-writing.st` 铁律："关键证据/道具/机密信息必须在前文有获取场景或合理铺垫，不得凭空拥有。"

### D. 语言质量系统（解决 #8 套路词 / #9 校对硬伤）

#### D1：套路词热度控制 — 接入 StyleGuardian + 词频检测

**根因**：`StyleGuardianAgent.checkConsistency()` 存在但未接入章节写作主流程；无词频检测。

新建 `service/ClicheDetector.java`（纯规则，无 LLM）：
- 维护通用反应词清单（题材无关）：目光一凝/一凛/一变/一沉、脸色一变/一白/一青、嘴角一抽、瞳孔一缩、倒吸一口凉气、心中一凛、暗道不好...
- 每章统计本章 + 最近 5 章高频反应词，某词超阈值 → 加入"本章禁用词表"
- 注入 ContextAssembler："本章禁止使用以下高频反应词：[列表]"

同时把 `StyleGuardianAgent.checkConsistency()` **接入** `NovelOrchestrator.checkContinuityAfterWriting()`（当前未接入），`style-check.st` 增加高频反应词检查项。

#### D2：一致性门禁 — ConsistencyGate

**根因**：无章号一致性检查；无时代用语检查。

新建 `service/ConsistencyGate.java`（纯规则）：
1. 章节编号：正文"第N章"是否与实际 chapter_index 一致
2. 角色名一致性：复用 EntityGraph 别名表
3. 时代用语：`GenreRuleProvider` 每题材提供 `forbiddenModernTerms`（古风禁"补钙/数据库/系统"，科幻禁"真气/丹田"...）

## 四、LLM 调用成本控制

新增 4 个 LLM 检测，每章多 3-4 次调用。降本策略：
1. SceneClassifier 用最便宜模型（分类任务 7 选 1）
2. ClicheDetector 和 ConsistencyGate **纯规则无 LLM**
3. AbilityGuard + CausalityGuard 可合并为一次调用
4. StyleGuardian 已存在，只是接入

**净增：每章 +2 次 LLM 调用**（1 次合并能力+因果检测 + 1 次场景分类）。

## 五、实现顺序（按依赖关系）

| Step | 子系统 | 优先级 | 理由 |
|:-:|---|:-:|---|
| 1 | **C1 伏笔闭环** | 🔴 最高 | 问题最严重（信物遗忘），四重失效需系统性修复 |
| 2 | **B2 场景多样性** | 🔴 高 | 激活死代码 + 新建场景分类，直接解决套路化 |
| 3 | **D1 套路词** | 🟠 中高 | 纯规则快速见效，接入已有 StyleGuardian |
| 4 | **A1 对手智谋** | 🟠 中高 | prompt + 字段增强，直接解决反派降智 |
| 5 | **B1 信息密度** | 🟡 中 | 共享 STRUCTURE 检测（依赖 B2） |
| 6 | **A2 弧光调度** | 🟡 中 | 共享 Character 字段（依赖 A1） |
| 7 | **A3+C2 能力+因果** | 🟡 中 | 共享 ability 字段（依赖 A1） |
| 8 | **D2 一致性门禁** | 🟢 低 | 纯规则，独立 |
| 9 | **E2E 验证** | — | 重新生成一篇不同题材小说 + 读者评审对比 |

## 六、验证标准

每个子系统完成后：`mvn compile && mvn test` 通过（新增对应单测）。
全部完成后 E2E 验证：重新生成一篇**不同题材**（如悬疑或武侠）的小说，用读者评审 Agent 对比 Phase 9 vs Phase 10，验证反派降智次数↓、配角出场频率↑、场景结构多样性↑、伏笔回收率↑、套路词频率↓。
