# Phase 12：百万字长篇小说架构优化方案

## 目标
支持单部小说达到 100 万字（约 250 章、10+ 卷），从当前 5-10 万字能力跃升到百万字级别。

## 瓶颈 → 方案映射

| # | 瓶颈 | 严重度 | 核心问题 | 方案 |
|:-:|---|:---:|---|---|
| 1 | 大纲生成 | 🔴高 | 一次性生成、maxTokens 12000、totalChapters 硬编码 24 | **K1：分层大纲** |
| 2 | 写作循环 | 🔴高 | HTTP 同步阻塞、250 章无法在单请求完成 | **K2：异步写作引擎** |
| 3 | 数据库性能 | 🔴高 | 零索引、全表扫描、向量库每次 upsert 全文件重写 | **K3：数据库优化** |
| 4 | 上下文膨胀 | 🟡中 | 卷摘要全量注入 + HIGH 伏笔永不裁剪会膨胀 | **K4：记忆分层压缩** |
| 5 | 摘要质量 | 🟡中 | 卷摘要 maxTokens 500 偏低、无限增长 | **K4（合并）** |
| 6 | 卷结构 | 🟡中 | chekhovAudit 全表扫描 | **K3（合并）** |

## K1：分层大纲生成 — 从一次性→分卷分批

### 根因
`PlotterAgent.plan()` 一次性生成全部章节大纲（`PlotterAgent.java:39-105`），maxTokens 12000，250 章需要 3-7 万 token 输出——不可能。totalChapters 硬编码 24（`NovelOrchestrator.java:265`）。

### 方案：三层大纲架构

```
第一层：全书总纲（1 次 LLM 调用）
  - 核心冲突、主角弧光、卷数规划、每卷一句话梗概
  - 输出：N 卷的标题+梗概+章数范围

第二层：卷级大纲（每卷 1 次 LLM 调用，写作到该卷时才生成）
  - 本卷的详细章节梗概（每章 beats/climax/cast/tension/伏笔）
  - 输入：全书总纲 + 前卷摘要 + 本卷梗概
  - 延迟生成：写完前一卷才生成下一卷大纲

第三层：章节正文（已有，不变）
```

| 改动 | 文件 | 内容 |
|---|---|---|
| 总纲生成 | `PlotterAgent.java` 新增 `planMasterOutline()` | LLM 生成全书总纲（卷数+每卷梗概+章数），maxTokens 4000 |
| 分卷大纲 | `PlotterAgent.java` 新增 `planVolume()` | LLM 生成单卷详细章节大纲，maxTokens 8000 |
| 总纲模板 | 新建 `prompts/master-outline.st` | 输入 concept+题材→输出全书 N 卷的标题/梗概/章数 |
| 分卷模板 | 新建 `prompts/volume-outline.st` | 输入总纲+前卷摘要→输出本卷详细章节 |
| totalChapters 参数化 | `NovelOrchestrator.java` | 硬编码 24→从 WritingPreferences 或项目配置读取 |
| 延迟生成 | `NovelOrchestrator` | 写到新卷时检查该卷大纲是否存在，不存在则调用 planVolume 生成 |
| 大纲扩展 | 新增 `NovelOrchestrator.extendOutline()` | 允许在已有大纲基础上追加新卷（续写能力） |

**关键设计**：
- 全书总纲在构思阶段一次性生成（轻量，~4000 token）
- 每卷详细大纲在写到该卷第一章前才生成（延迟加载）
- 写完一卷后，下一卷的大纲才被创建——避免一次性生成 250 章

## K2：异步写作引擎 — 从同步阻塞→后台任务

### 根因
`OrchestratorController.writeAll` 同步调用 `runWritingLoop`（`OrchestratorController.java:46-58`），250 章需要数小时，HTTP 必然超时。无 `@Async`/线程池/SSE。

### 方案：后台写作任务 + 进度查询

| 改动 | 文件 | 内容 |
|---|---|---|
| 写作任务状态 | 新建 `domain/WritingTask.java` | taskId/projectId/status(RUNNING/PAUSED/COMPLETED/FAILED)/currentChapter/totalChapters/errors |
| 新建表 | `SqliteSchemaInitializer` | `writing_tasks` 表 |
| 异步执行 | 新建 `service/WritingTaskExecutor.java` | 用 `ExecutorService` 单线程后台执行 runWritingLoop，更新 task 状态 |
| API 端点 | `OrchestratorController` | `POST /write-all` 改为启动后台任务返回 taskId；`GET /writing-tasks/{taskId}` 查进度；`POST /writing-tasks/{taskId}/cancel` 取消 |
| 前端 | `RunConsole.tsx` | 连续写作改为轮询 task 状态显示进度条 |
| 断点续写 | `WritingTaskExecutor` | 幂等检查已有（`NovelOrchestrator.java:374-381`），中断后重新启动 task 自动续写 |

**关键设计**：
- write-all 不再阻塞，立即返回 taskId
- 前端每 5 秒轮询 task 进度
- 任务状态持久化到 DB——服务重启后可恢复
- 支持取消（设置 cancel flag，写作循环每章检查）

## K3：数据库优化 — 索引 + 查询优化 + 向量库

### 根因
全库零索引（`SqliteSchemaInitializer` 无 CREATE INDEX）；`getTotalWordCount` 全量加载正文求和；向量库每次 upsert 全文件重写（`EmbeddedVectorStore.java:40-43`）。

### 方案

| 改动 | 文件 | 内容 |
|---|---|---|
| **加索引** | `SqliteSchemaInitializer` | 所有表的 project_id/chapter_index/source_id/target_id/resolved/type 列加索引 |
| **SUM 聚合** | `SqliteNovelRepository` | 新增 `getTotalWordCount(projectId)` 用 `SELECT SUM(word_count)`，替换全量加载 |
| **分页查询** | `SqliteNovelRepository` | `findChaptersByProject` 增加 offset/limit 重载（章节列表不全量加载正文） |
| **轻量章节列表** | `SqliteNovelRepository` | 新增 `findChapterMeta(projectId)` 只返回 index/title/wordCount（不含 content） |
| **向量库批量持久化** | `EmbeddedVectorStore` | upsert 不立即 persist，改为标记 dirty + 定期/批量持久化（每 N 次 upsert 或每章结束后 flush） |
| **chekhovAudit 优化** | `SqliteNovelRepository` | `findForeshadowingsByProject` 增加 chapter 范围过滤（WHERE planted_at_chapter BETWEEN ? AND ?） |

## K4：记忆分层压缩 — 卷摘要控制 + 远期衰减

### 根因
卷级摘要全量注入（`ContextAssembler.java:191-215`），10+ 卷时膨胀；HIGH 伏笔永不裁剪会累积；卷摘要 maxTokens 仅 500（`MemoryManagerAgent.java:37`）。

### 方案

| 改动 | 文件 | 内容 |
|---|---|---|
| **卷摘要上限** | `ContextAssembler.buildRecentSummary()` | 最多注入最近 3 卷详细摘要；更早的卷合并为 1 条"远期摘要" |
| **远期摘要合并** | 新建 `NovelOrchestrator.compressDistantSummaries()` | 每 5 卷把旧卷摘要合并成一条"第1-5卷综合摘要" |
| **卷摘要预算提升** | `MemoryManagerAgent.java` | maxTokens 500→1500 |
| **伏笔注入上限** | `ContextAssembler.buildForeshadowings()` | HIGH 伏笔也设上限（最多 15 条），超过的按 suspenseChapters 降序裁剪 |
| **Token 预算提升** | `ContextAssembler` | TOKEN_BUDGET 12000→16000（适配更长上下文） |

## 实现顺序（按 harness 规范拆分特性）

| Feature | 方案 | 优先级 | 理由 |
|:-:|---|:-:|---|
| **K3-F1** | 数据库索引+SUM聚合+轻量查询 | 🔴最高 | 性能基础，其他特性依赖它 |
| **K3-F2** | 向量库批量持久化 | 🔴高 | 随章数线性恶化的性能债 |
| **K2-F1** | 异步写作引擎（WritingTask+Executor+API） | 🔴高 | 解除 HTTP 超时限制 |
| **K1-F1** | 全书总纲生成（master-outline） | 🔴高 | 解除大纲一次性生成限制 |
| **K1-F2** | 分卷延迟大纲生成（volume-outline） | 🔴高 | 让 250 章大纲可行 |
| **K1-F3** | totalChapters 参数化 + 大纲扩展 | 🟡中 | 让用户可设目标字数 |
| **K4-F1** | 卷摘要控制+远期合并 | 🟡中 | 防止上下文膨胀 |
| **K4-F2** | 伏笔注入上限+Token预算提升 | 🟡中 | 防止伏笔膨胀 |

每个 Feature 完成后：mvn compile + mvn test 通过 + 提交。

## 验证标准
- K3 完成后：250 章模拟数据下 getTotalWordCount < 10ms（之前会 OOM）
- K2 完成后：write-all 立即返回 taskId，前端轮询显示进度
- K1 完成后：能生成 10 卷×25 章的分批大纲
- K4 完成后：第 200 章上下文 token 预算不超过 16000
