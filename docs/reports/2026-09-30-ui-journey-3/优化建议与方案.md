# 第三轮旅程缺陷分析与优化方案 — 2026-09-30

配套文档：同目录《整体使用报告.md》（缺陷编号 F-1..F-11 / 观察项 O-1..O-5 均出于此）。本文回答两个问题：**这些问题说明系统哪里有病根**，以及**按什么顺序怎么修**。所有方案已对齐仓库硬规则（Bugfix gate：先 failing test；prompt 改动：e2e 基线对比 + bless）。

---

## 1. 总体判断：缺陷分布模式

把 11 项缺陷按子系统归堆，模式非常清晰：

| 子系统 | 缺陷 | 占比 |
|---|---|---|
| 长任务/工作权/重试基础设施 | F-1、F-6、F-10、F-11、F-7 | 5/11 |
| 作者协作 UX（审阅-裁决-批准链路） | F-2、F-4、F-9 | 3/11 |
| 局部 UI 状态 | F-5、F-8 | 2/11 |
| 模型路由/环境 | F-3 | 1/11 |

**核心结论：内容生产链路（构思→大纲→写作→检查→仲裁重写）在本轮 9 章 3.2 万字中被验证是成熟的，质量门禁的检出质量（能力越界/凭空证据/伏笔错收）甚至超出预期。系统性短板集中在一条轴上——"长耗时操作的生命周期管理"：任务提交后看不见（F-1）、失败后停不下来（F-6）、失败后不自愈（F-10）、完成后锁不放（F-11）、崩溃后锁残留（F-7）。**这五项不是五个孤立 bug，是同一块缺失的基础设施被五个入口各自暴露。因此第一优先级不是逐个打补丁，而是补上这块横切设施（方案 A）。

第二个模式：**协作链路的"最后 100 米"断裂**。裁决台账、屏障批准、版本化批准门禁这些治理机制后端都在且可审计，但入口经常不可达或时机不对（F-9 无内联入口、F-4 批准后不恢复、F-11 锁延迟导致"检查点上操作全 409"）。读者在本轮被迫 4 次绕道 API——功能等价但说明 UI 通路没有承受住真实节奏。

环境问题（本机代理掐长连接、上游 Token Plan 对 >3-5min 流式掉线、glm 122s 确定性空响应）已通过去代理重启 + 全路由收敛 qwen3.8-flash 缓解，不计入产品缺陷，但产品应当对这类上游不稳更有韧性（见 §5）。

## 2. 方案 A（横切，第一优先级）：长任务与工作权生命周期统一治理

一个 epic 收编 F-1 / F-6 / F-10 / F-11 / F-7，四件事：

### A1. 统一长任务注册表 + 单一轮询端点（修 F-1，同时补 reader-review 缺失的轮询端点）

- **现状**：`LongTaskService` 本身是共享单例（kind 无关，内存态），但轮询 GET 散落两处且前缀不同：`RevisionController`（`/api/projects/{id}/revisions/long-tasks/{jobId}`，RevisionController.java:46）、`ReviewDecisionController`（`/chapters/{chapterIndex}/long-tasks/{jobId}`，ReviewDecisionController.java:212）；`ReaderReviewController` 的 javadoc 承诺轮询 long-tasks 但**根本没有实现该端点**。前端 `getLongTask` 统一拼 `/projects/{id}/long-tasks/{jobId}`（client.ts:663）→ 全部 404。
- **方案**：新增 `LongTaskController`：`GET /api/projects/{id}/long-tasks/{jobId}` 直接委托 `longTasks.get(id, jobId)`（项目隔离与 404 语义照抄现有实现）。保留旧端点兼容，前端不动。约 30 行 + 1 个 WebMvc 测试。
- **为什么不做前端改路径**：三处任务 kind 会继续增殖，统一端点一次修复全部现有与未来入口；前端零改动零发版。
- **附带收益**：reader-review / agent-revision-preview / recheck-async 三个特性同时复活，可用一次真实 UI 旅程回归验证。
- **验收**：`mvn test -Dtest=LongTaskUnifiedPollingTest`；手工在 18095 上走一次「让 Agent 修改」预览 → 预览渲染成功。

### A2. 阶段级重试上限 + 显式失败终态（修 F-6）

- **现状**：MEMORY_SUMMARY 阶段失败后在本阶段内无限退避重试（事件单条 durationMs 累计 2,942,776ms ≈ 49 分钟），章状态永远停在 POST_PROCESSING，无终态、无 UI 感知、无手动出口。`DefaultLlmGateway` 的 cooling/nextAttempt 是 provider 级熔断，不约束调用方的阶段级重试次数。
- **方案**（三层）：
  1. `ChapterPostProcessor` 每个阶段加 attempt 上限（建议 3 次，指数退避），耗尽后章状态置 **POST_PROCESS_FAILED**（新枚举值），事件 `POST_PROCESS_STAGE_FAILED{stage, attempts}` 落盘；
  2. 章节管理页对失败章给「重跑后处理」按钮（按 stage 粒度重跑，幂等——真典收割/台账本就有幂等检查）；
  3. 记忆摘要调用做**上下文裁剪**：本轮正常章写 137-186s 稳定成功、只有修订重写/记忆摘要这类超大 prompt 撞 3-5min 上游掉线——摘要只需近期正文+分层摘要，不该带全书快照全量。
- **测试**：failing test 先行——用 Scenario 网关构造连续 NETWORK，断言 3 次后进入 POST_PROCESS_FAILED 而非无限重试；再断言重跑入口可恢复。
- **验收**：`mvn test -Dtest=ChapterPostProcessRetryTest`；制造一次 provider 失败，UI 上章状态可读、可重跑。

### A3. 工作权锁：心跳 + TTL + 启动清扫（修 F-11 / F-7）

- **现状**：`WritingTaskExecutor` 在 finally 释放 coordinator token，但本轮两次观察到后处理日志结束后锁仍被占 ~10 分钟（409 SYNC_WORK_BUSY），以及 JVM 重启后持久化的操作锁残留（横幅"审阅修订中 · 已 18 分钟"，靠 UI「取消该操作」逃生口自救——这个逃生口设计得很好，保留）。
- **方案**：
  1. `ProjectWorkCoordinator` 的 token 增加持有者心跳（如 30s 续期）；领取/校验时 TTL 过期即视为死锁可抢占（写路径仍互斥，只是把"死锁"变"可恢复"）；
  2. 应用启动时清扫持久化锁表中无进程绑定的记录（或标记 STALE 由 UI 提示一键接管）；
  3. 检查点暂停（WRITING→PAUSED_AT_CHECKPOINT）时机上显式释放同步操作锁——这是 F-11 十有八九的直接病因：暂停后某个收尾路径没有走到 release。
- **测试**：failing test——模拟 worker 停止心跳，断言锁在 TTL 后可被新请求获取；重启上下文测试断言锁表被清扫。
- **验收**：`mvn test -Dtest=WorkCoordinatorTtlTest`；重启实例后无需点「取消该操作」即可继续。

### A4. 长任务对 provider 冷却的韧性（修 F-10）

- **现状**：reader-review 两次失败——一次撞冷却立即判失败、一次 NETWORK 直接失败，`LongTaskService` 无重试语义（任务内存态，重启即失）。
- **方案**：`LongTaskService.submit` 增加可选 `retryOnLlmUnavailable`（延迟入队：冷却结束时刻重投，最多 2 次）；任务增加 `FAILED_RETRYABLE` 状态。依赖 A1 的统一端点让前端能看到失败原因与重试按钮。
- **验收**：`mvn test -Dtest=LongTaskRetryTest`。

## 3. 协作链路"最后 100 米"（Phase 2）

### B1. 批准阻塞提示内联裁决入口 + DEFER 语义显式化（修 F-9）

- **现状**：批准被拒的提示（"批准未生效：存在未解决的 HIGH…"）把问题列全了但**原地没有任何处置按钮**；三类分层区的"作为创作例外保留"按钮在真实操作中多次定位失败；DEFER 不满足批准门禁，与"暂挂=推迟处理"的直觉相反且无解释。
- **方案**：
  1. 阻塞提示内每条 HIGH 直接内联三个快捷裁决（误报/例外/暂挂），复用 `POST /dispositions`；
  2. DEFER 选项旁明示"暂挂不解除本章阻塞，仅登记到第 N 章"；或者引入**带簿放行**（approve-with-defer：全部 HIGH 均 DEFER 且 deferUntilChapter ≤ 剩余章数时允许放行，台账记 DEFER_BLOCKED_OVERRIDE）——推荐后者，语义与"暂挂到卷末统一修订"的真实工作流吻合（本轮 9 条 HIGH 全是这种诉求）；
  3. 顺带修"已裁决项仍显示未处置"的列表刷新问题（dispositions 变更后分类视图不重取）。
- **测试**：先写 failing test 复现"DEFER 后 approve 仍 409 且 UI 无入口"，再实现内联裁决；带簿放行需要新增 approval 分支的集成测试（审计行必须落库）。

### B2. 框架修改意见 → 既有人物卡定向修订（修 F-2）

- **现状**：`reviseInitialSetup`（NovelOrchestrator.java:859）对人物层只做"按大纲补新卡 + 点名零出场"（NCS-090 的 `syncCharactersFromOutline`），`instructions` 里点名既有卡的意见（合并殷素更/裴无秤、去记账腔）被静默丢弃——上一轮 A-1 修了一半。
- **方案**：意图门控扩展——当 instructions 中出现与既有卡**姓名精确匹配**（14 张卡名做词边界匹配，避免误伤）时，对该卡调用 CharacterDesigner 修订（输入=原卡+作者意见，输出=候选新卡版本，走 `previewCharacterUpdate` 已有的预览-确认链落库，保持作者批准制）。不点名则维持现状。合并/删除卡属于结构性操作，**不做自动合并**，仅在返回摘要中提示作者手动处置。
- **测试**：failing test——instructions 含"殷素更去记账腔"时断言殷素更卡内容变化；不含人名时断言既有卡零变动（防搭车改写）。
- **风险**：人物卡变化会改变后续章写注入 → 属于影响产出质量的改动，合入前跑 `./scripts/e2e.sh` + `compare-baseline.py`，bless 需附重建理由。

### B3. 批准后自动恢复 + 错误信息清理（修 F-4）

- **现状**：per-chapter 节奏下批准≠恢复，需再点「继续协作」；且 writing-tasks 的 errorMessage 残留上一状态文案（"请先处理待审核内容"在已处理后仍显示）。
- **方案**：`review-decisions` 批准成功且无其他 pending 检查点时，后端直接触发 resume（前端按钮语义改为"暂停/恢复"开关）；任务状态转移时清空 errorMessage 或按当前态重算文案。
- **测试**：集成测试断言批准后 5s 内项目回到 WRITING；单测断言状态转移清错。

## 5. 环境与上游韧性（运维项 + 小产品项）

1. **load-env.sh 默认为 LLM 域名加 no_proxy**（token-plan.cn-beijing.maas.aliyuncs.com、open.bigmodel.cn）——本轮 49 分钟卡死的放大器就是服务进程继承了 `http_proxy=127.0.0.1:9098`。一行改动，收益极大。
2. **模型库「测试此模型」按钮**：新增模型/切路由时发一个小请求（max_tokens=32）验证连通+鉴权，失败即时不入库；避免"新建项目第一个章写在默认坏路由上必卡"（F-3 的产品化收尾，本轮读者被迫中途排障）。
3. **诊断页标红**：`diagnose.sh` 已有 LLM 统计，前端模型库页对"连续 N 次 EMPTY_RESPONSE/NETWORK 的路由"给警示条。
4. **修订重写瘦身**：见 A2.3——大 prompt 长调用是上游掉线的高发区，修订重写只送目标章+必要上下文，不送全书。

## 7. 不建议做的（反模式）

- **不要**为绕过代理/上游掉线把流式改非流式或缩短 request-timeout——900s 超时本身是对的，病灶在上游与代理，改超时只会把长生成截断成 EMPTY_RESPONSE。
- **不要**让 DEFER 直接无条件放行（破坏"未解决不出版"的审计语义）——用 §3-B1 的带簿放行（有界的、留痕的）替代。
- **不要**在 F-1 修复中给每个 Controller 各自加路径变体——统一端点一次解决，路径前缀越增殖越乱。
- **不要**自动合并/删除人物卡（F-2）——结构性变更必须作者显式操作，Agent 只提供修订候选。
- **不要**把桥段重复检测整体砍掉——检出"连续 3/4 章对抗博弈"的趋势数据是有价值的，要修的是口径（O-4）不是功能。
