# 图数据库 + LLM 实体提取 + 质量闭环方案

**适用模型：DeepSeek V4 Flash / GLM-5.2（云端大模型），不做弱模型兼容**

## 核心流程

```
每章写作流程:
  1. ContextAssembler 组装上下文
     ├── 从图数据库召回实体 → buildEntityConsistencySection()    ← 新增
     ├── 根据章位置+质量反馈 → buildWritingConstraints()         ← 新增
     └── 从上卷评价记录 → buildQualityFeedbackSection()          ← 新增
  2. ChapterWriterAgent 写正文
  3. EntityExtractorAgent 提取实体+关系 → 存入图数据库            ← 新增
  4. ContinuityChecker 检查连续性 (现有)
```

## 一、图数据库存储层

### SQLite 新增 3 张表

```sql
-- 实体表：规范名 + 别名 + 类型 + 首次/最近出现章节
CREATE TABLE entities (
    id TEXT PRIMARY KEY,
    project_id TEXT NOT NULL,
    name TEXT NOT NULL,
    type TEXT NOT NULL,          -- CHARACTER|ITEM|LOCATION|TECHNIQUE|FACTION|EVENT|CONCEPT
    aliases TEXT,                -- JSON ["苏辰","陈苏"]
    first_seen_chapter INTEGER,
    last_seen_chapter INTEGER,
    metadata TEXT,               -- JSON
    created_at TEXT, updated_at TEXT
);

-- 关系边表
CREATE TABLE entity_edges (
    id TEXT PRIMARY KEY,
    project_id TEXT NOT NULL,
    source_id TEXT NOT NULL REFERENCES entities(id),
    target_id TEXT NOT NULL REFERENCES entities(id),
    relationship TEXT NOT NULL,   -- OWNS|LOCATED_IN|MEMBER_OF|CREATES|USES|ALLY|ENEMY|KNOWS
    weight REAL DEFAULT 1.0,
    metadata TEXT,
    created_at TEXT
);

-- 卷末评价记录
CREATE TABLE evaluation_records (
    id TEXT PRIMARY KEY,
    project_id TEXT NOT NULL,
    volume_index INTEGER,
    scores_json TEXT,
    overall_score INTEGER,
    summary TEXT,
    improvement_notes TEXT,
    created_at TEXT
);
```

### 新增领域对象

| 类 | 字段 |
|----|------|
| `Entity` | id, projectId, name, type(enum), aliases(List), firstSeenChapter, lastSeenChapter, metadata |
| `EntityEdge` | id, projectId, sourceId, targetId, relationship(enum), weight, metadata |
| `EvaluationRecord` | id, projectId, volumeIndex, scores(Map), overallScore, summary, improvementNotes |

## 二、EntityExtractorAgent（LLM 提取实体+关系）

### 工作方式

与 QualityEvaluationAgent 相同模式：调用 LLM + 解析 JSON 输出。

```
每章写完后：
  EntityExtractorAgent.extract(projectId, chapter)
    → 读取章节正文 + 已有实体列表（防重复）
    → entity-extraction.st 模板渲染
    → LLM 调用（路由 GENERAL 或新增 ENTITY_EXTRACTION 类型）
    → 解析 JSON → entities[] + edges[]
    → 写入图数据库
```

### 去重策略（Java 层，非 LLM）

1. LLM 返回的实体先按 name 精确匹配已有实体
2. 再按 aliases 匹配
3. 匹配上则更新 last_seen_chapter + 合并别名
4. 未匹配上则插入新实体

### prompt 模板 `entity-extraction.st`

```
你是小说实体提取专家。从章节正文中提取所有重要实体及其关系。

实体类型及提取要求：
- CHARACTER: 所有有名字的角色（主角、配角、反派），含仅在本章出场一次的角色
- ITEM: 具体物品（武器名、丹药名、法宝名、信物名、特殊材料名）
- LOCATION: 具体地点（宗门、秘境、城池、洞府、山脉、深渊）
- TECHNIQUE: 功法/技能/法术/阵法的名称
- FACTION: 势力组织（宗门、家族、教派、联盟）
- EVENT: 本章提及的历史事件或重要仪式
- CONCEPT: 本章核心的抽象概念或特殊规则

已有实体清单（如果正文中出现以下实体，type/name 必须与之一致）：
{{existingEntities}}

提取规则：
1. 只提取本章正文中实际【指名道姓】出现的实体，不要编造
2. 已有实体使用其规范名，已在已有清单中的不要重复创建
3. 别名：正文中使用的非规范名（如"苏兄"代"苏尘"）记录为 aliases
4. 关系：只提取明确的关系（A的B→A OWNS B；A在B→A LOCATED_IN B；A/B敌对→ENEMY）
5. 每条关系必须有原文依据

章节正文：
{{chapterContent}}

JSON 输出格式（只输出 JSON，不要其他内容）：
{
  "entities": [
    {"name": "规范名", "type": "CHARACTER", "aliases": ["别名1"], "description": "本章中的角色状态"}
  ],
  "edges": [
    {"source": "实体A", "target": "实体B", "relationship": "OWNS", "weight": 1.0}
  ]
}
```

### EntityGraphService

```java
@Service
public class EntityGraphService {
    // 写后：LLM 提取 + 图库写入
    void extractFromChapter(String projectId, Chapter chapter);
    
    // 写前：实体召回 → 格式化一致性文本
    String recallConsistencySection(String projectId, int currentChapter, 
                                     ChapterSynopsis synopsis);
    
    // 别名 → 规范名解析
    String resolveCanonical(String projectId, String rawName);
}
```

**recallConsistencySection 召回策略：**
1. 最近 5 章出现过的实体 → 优先召回
2. 本章场景地点/势力的 1 跳关系邻居 → 补充召回
3. 排序：recency > 关系权重 > 类型优先级
4. 每类最多 5 条，总量 ≤ 25

## 三、一致性注入（WritingContext + ContextAssembler）

### WritingContext 新增 3 个字段

```java
private String entityConsistencySection;    // 实体一致性提醒
private String writingConstraints;          // 量化约束
private String qualityFeedbackSection;      // 上卷质量反馈
```

### toSystemPrompt() 改造

在【写作铁律】后追加实体一致性块（system prompt，高优先级）：
```
【关键实体一致性（以下名称前文已确立，本章必须严格使用）】
■ 人物：苏尘、星瑶公主
■ 物品：断脉草、星髓币
■ 地点：星坠渊、天衡星宫
⚠️ 别名警告：「苏尘」不得写成"苏辰"
```

### toUserPrompt() 改造

在末尾追加（质量反馈 + 量化约束）：
```
【上卷质量评价反馈——改进方向】
总评：6/10。一致性(6/10)：药材名不一致。情节(6/10)：爽点密度不足。
本章改进：每章≥2个爽点，注意实体名称统一。

【本章刚性约束】
□ 必须包含至少 2 个爽点（信息差/反预期/智斗/情感反转）
□ 必须使用至少 1 个世界观独特设定
□ 场景节拍必须全部覆盖（共 N 个）
□ 章节结尾必须是一个悬念钩子
```

## 四、量化约束（chapter-writing.st）

在「反套路条款」后新增条件块：

```
{{#if writingConstraints}}
【本章刚性约束（逐条检查，遗漏即违规）】
{{writingConstraints}}
{{/if}}
```

约束生成规则（ContextAssembler.buildWritingConstraints）：
1. **爽点约束**：固定「至少 2 个爽点，类型与前章轮换」
2. **世界观约束**：固定「至少使用 1 个世界观独特设定」
3. **节拍覆盖**：dynamic → 从 ChapterSynopsis.beats 统计
4. **悬念结尾**：固定
5. **质量反馈**：dynamic → 从上卷 EvaluationRecord 提取

## 五、质量反馈闭环

### 改造 checkAndGenerateVolumeSummary()

```
// 现有
qualityEvaluationAgent.evaluate()
if score < 6: save ContinuityIssue

// 改造
EvaluationReport report = qualityEvaluationAgent.evaluate()
// 额外调用：生成改进建议（基于低分维度）
String improvementNotes = generateImprovementNotes(report)
// 持久化
save new EvaluationRecord(projectId, volumeIndex, scores, summary, improvementNotes)
// 保留现有：低分记录
if score < 6: save ContinuityIssue
```

### ContextAssembler.buildQualityFeedbackSection()

下一卷首章时调用 repository.findLatestEvaluation()，只注入低分维度（< 7 分）+ 改进建议。
