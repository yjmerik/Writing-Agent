## 二、单章生产管线实测

- 无重写章节约 15-20 分钟；带质量重写或补查 20-40 分钟；每章经 写作→连续性检查→一致性守卫→质量评审→（重写→复查）→暂停待人审。
- 读者评分：第1章 8/10、第2章 6/10、第3章 8/10、第4章 7/10、第5章 6/10、第6章 7/10、第7章 7/10、第8章 7/10、第9章 8/10、第10章 7/10、第11章 7/10、第12章 7/10。
- **字数逐章递减**：第1章 5,570 → 第2章 10,659 → 第3-12章普遍 3,400-5,000 字（远低于第 1-2 章规模，全书后半明显偏薄）。
- 真典收割每章 +8~9 条；伏笔候选持续新增；成本：249 次带归属的 LLM 调用，prompt 167 万 + completion 228 万 tokens，约 6.2 元（另有若干 `<NONE>` 归属调用未计入，见 A-3）。

## 四、缺陷与结构性问题（按严重度）

### A-1（P1）框架审阅「修改意见重写」只覆盖世界观，人物层反馈被静默丢弃
- 作者提交「为章纲 8 个关键配角补人物卡、处置 5 张零出场卡」，修订执行并自动批准，但人物卡 API 前后完全一致（evidence-characters-before-revision.json），仅真典条目被改名。
- 根因：`NovelOrchestrator.reviseInitialSetup`（NovelOrchestrator.java:848）只调 `worldBuilder.propose`→`replaceEntries`，CharacterDesigner 不在路径内；UI 无「人物不在修订范围」提示。
- 上轮旅程同类发现（人物卡与章纲脱节：8 个章纲关键配角无卡、5 张零出场卡）在本轮完整复现，且这次的正规修订入口证明无法修复该脱节。

### A-2（P1）「重新检查」只跑 continuity 检查器，清不掉其他检查器的未查清项
- ch2 consistency-guard 产生 UNKNOWN（07:10:16），「重新检查」按钮触发 /recheck（真实执行 4.5 分钟），落库的是 `continuity` SUCCESS 信封；`consistency-guard` UNKNOWN 原样保留（check_results 表 `2|consistency-guard|UNKNOWN|07:10:16` 与 `2|continuity|SUCCESS|09:33:45` 并存）。
- 根因：`NovelOrchestrator.recheckChapter`（NovelOrchestrator.java:3171）只调 `continuityChecker.check`，信封按 (chapter, checker) 存储。
- 影响：本轮 12 章出现 5 个非 continuity 未查清（3×consistency-guard、2×correction-verification），全部无 UI 出路。
- 附：首次点击重检（15:16）无服务端动作、无报错，前端一直「重检中」；17:29 第二次才真正执行——前端乐观状态与服务端工作权不同步。

### A-8（P0）终局死锁变体：三个机制叠加，书无法通过任何 UI 路径到达 FINAL
1. 门禁硬条件 `unknownCount>0` 即 FAIL（NovelOrchestrator.java:2505「必查检查尚未查清」）——12 章里出现 5 个 UNKNOWN（概率约 40%/章），任何一次 LLM 输出异常都会埋雷；
2. A-2 使这些 UNKNOWN 无法通过「重新检查」清除；
3. NCS-082 追加回收卷成功（第 13-20 章），但 NEEDS_REVISION 状态下动作策略禁止 WRITE_CHAPTER/WRITE_ALL（「当前状态 NEEDS_REVISION 不允许写作」）——回收章无法创作，mustResolve 72 条只能逐条手工结清；且即使全部结清，条件 1 仍阻断。
- 实证：重审 FAIL 日志 `成书门禁 FAIL: 5 项必查检查尚未查清（UNKNOWN/INVALID）`；`3#continuity VALID_EMPTY` 落库后 `3#correction-verification UNKNOWN` 未变；追加回收卷后 `availableActions: WRITE_CHAPTER=false`。
- 上轮 P0（完结死锁）的三个成因已被 NCS-077..079 修复，但门禁的 unknown 标准与 A-2 的组合构成了新的死锁变体。建议：a) recheck 按 card.checker 路由到对应检查器；b) 屏障担责批准（版本化批准）应同时把该章 UNKNOWN 信封标记为「作者担责豁免」或降级；c) NEEDS_REVISION 下允许写作回收卷章节（或追加回收卷时自动退出 NEEDS_REVISION）。

### A-4（P1）章级 AI 修订预览与超时预算错配 + 失控长输出
- ch2 预览第 1 次：服务端真实执行 9.4 分钟（52,689 completion tokens，LLM_TRUNCATED），前端 300s 超时中止（「signal is aborted without reason」）；第 2 次：240s 后「Failed to fetch」（本机代理 127.0.0.1:9098 掐断长连接）；服务端线程持续流式读取，UI 无进度可见。
- 建议预览/重检改异步任务 + 轮询；对修订类输出设 max_tokens 与长度校验；前端超时按任务类型分级。

### A-3（P2）telemetry：recheck 与 checkpoint 修订的 LLM_CALL 无 projectId
- `05:27:45 LLM_CALL <NONE> WORLDBUILDING`（AFTER_INITIAL_SETUP 修订）、`09:33:45 LLM_CALL <NONE> CONTINUITY_CHECK`（recheck）。NCS-086 已覆盖预览（预览调用归属正确 ✅），但 `CheckpointController.withRevisionWork` 与 `ReviewDecisionController.recheck` 两条路径的 EventContext 未传播。

### A-5（P2）篇幅压缩后伏笔台账不回收（承上轮 P1-4）
- 压缩后台账条目回收章号仍指向已裁剪章（8 条 HIGH 指向 13-24 章），无逐项处置 UI、无提示。回收债务最终由成书门禁引爆（72 条必须回收）。

### A-6（P3）杂项
- 「审阅内容」按钮打开章节审查面板抽屉，与内联审阅卡并存易混淆（遮罩挡主页批准按钮）。
- 章节字数逐章递减（10k→3.4k），后半部明显单薄，无任何提示或干预。
- 「写作受阻」chip 在构思期即出现（有 tooltip 解释，语义准确但易误读为故障）。
- 环境：09-26 00:20 `target/*.jar` 被外部进程重建，运行中 JVM 出现 `NoClassDefFoundError`（WarResourceSet/Logback）——热替换运行中 fat jar 会直接损坏实例（与本项目「单实例长跑」用法冲突，值得在 init.sh/文档中提示）。

### ~~A-7（P2）SPA 深链转发失效~~（已撤案）
- 复验（2026-09-26，jar 重建导致 JVM 损坏修复后重启实例）：`GET /project/{id}/chapter/10` 返回 200 且正确返回 index.html。原 500「No static resource index.html / NoClassDefFoundError」是 00:20 外部进程重建运行中 fat jar、JVM 类加载损坏期间的假象，非产品缺陷。保留环境教训（见 A-6）。

## 七、结论与建议优先级

1. **P0（A-8）**：修复「unknownCount 门禁 + recheck 检查器错位 + NEEDS_REVISION 禁写回收卷」三重死锁——否则任何一本在写作期出现一次 guard/verification 输出异常的书都到不了 FINAL。
2. **P1（A-2）**：recheck 按 (chapter, checker) 路由；屏障担责批准覆盖该章 UNKNOWN。
3. **P1（A-1）**：框架审阅修订纳入人物层，或明示范围。
4. **P1（A-4）**：同步长事务改异步任务 + 进度；输出长度治理。
5. **P2（A-3/A-5）**：EventContext 补 propagation；压缩时同步收缩台账。（A-7 经复验为环境误报，撤案）
