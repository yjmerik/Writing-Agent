01 · Closed Loop

闭环拓扑：八段连续门禁

从需求到基线，每一段都有明确入口、机制与出口。任意一段失败都会回流到诊断门与 TDD 门，禁止跳章。

  • 入口节点（高亮边框）：闭环的关键门禁，每一道都设有可机器验证的出口。
  • 正向流（青色实线弧）：Spec → Backlog → TDD → CI → E2E → Diagnosis → Feedback → Baseline，顺时针推进。
  • 失败回流（琥珀虚线）：诊断门的失败分类经 Bug Feedback 登记为 bug feature，回到 TDD 门，先写复现测试再修复。
  1. 01
    Spec新需求 / 失败回流 → 写 spec（目标 / 非目标 / 验收标准）
  2. 02
    Feature Backlog登记 feature_list.json，每条带 acceptance + verify_cmd
  3. 03
    TDD / Bugfix Gatefeature 实现鼓励 TDD；修 bug 是硬规则：先 failing test 复现再改
  4. 04
    Init / CI./init.sh fail-fast + Maven CI 门禁
  5. 05
    Record / Replay E2Ee2e.sh 录制 / 回放；多章闭环尚未完成，详见证据台
  6. 06
    Structured Diagnosisdiagnose.sh 聚合失败分类与 LLM 统计
  7. 07
    Bug Feedback登记 type:bug feature → 回到 03 门
  8. 08
    Quality Baselinecompare-baseline.py 容差判定；golden 基线尚未 bless
02 · Gates

门禁卡：入口 · 机制 · 出口

每张卡对应闭环图上的一个节点。出口条件都可被一条命令或一个文件状态验证。

01

Spec

入口
新需求，或来自诊断门的失败回流
机制
复制 docs/specs/TEMPLATE.md 为日期前缀 spec，填目标 / 非目标 / 验收标准 / 影响面
出口
spec 写完且可拆为 1–3 文件改动的 feature
02

Feature Backlog

入口
已批准的 spec
机制
追加 feature_list.json，每条必带 acceptance 与 verify_cmd
出口
feature 可独立验证、已标注依赖
03

TDD / Bugfix Gate

入口
选定一个 feature，或来自 07 门的 bug feature
机制
feature 实现鼓励 TDD（先写 / 更新测试再改实现）；修 bug 是硬规则——必须先写 failing test 复现，再改实现，不允许直接改
出口
该 feature / bug 的 mvn test 由红转绿
04

Init / CI

入口
实现完成
机制
./init.sh fail-fast 验证编译 / 测试 / 20 模板 / 前端；.github/workflows/ci.yml Maven 门禁
出口
95+ 测试 · 0 failures · 模板变量无错配
05

Record / Replay E2E

入口
绿色构建
机制
e2e.sh 三模式；指纹按 taskType+prompt+history 的 SHA-256 命名，updatedAt 归一化；缺 fixture fail-fast
出口
产出 e2e-report.json · 0 LLM 错误 · 0 章节失败
06

Structured Diagnosis

入口
events.jsonl（LLM_CALL / LLM_ERROR / CHAPTER_*）
机制
diagnose.sh 聚合失败分类、LLM 统计、最近章节
出口
给出最高频失败与修复起点建议
07

Bug Feedback

入口
诊断门的失败分类
机制
按需求拆分协议登记 type:bug feature，evidence 引用诊断输出
出口
failing test 复现该 bug → 回到 03 门
08

Quality Baseline

入口
e2e-report.json
机制
compare-baseline.py 对比 baselines/golden.json，容差判定 PASS / FAIL
出口
PASS（无退化），或人工审阅后 --bless 更新基线
