## p9-1: 章节长度保障 — LengthGuard

### 根因
- `ChapterWriterAgent.java:122` 门槛 500 字 → 应为 2000+
- `NovelOrchestrator.java:313` ReaderReview 重写后 `>= 500` 就替换原文 → 无长度退化保护
- `rewriteForCorrection()` 无长度保证

### 方案

**1. 提升最低字数门槛**
- `ChapterWriterAgent.write()`: 500 → `MIN_CHAPTER_LENGTH = 2000`
- 写后如果 < 2000 字，重试（已有重试逻辑，只需改阈值）

**2. 重写长度保护**
- `NovelOrchestrator.runWritingOneChapter()` ReaderReview loop 中：
  - 重写后如果 `newContent.length() < original.length() * 0.7`，**拒绝替换**，保留原版
  - 即：重写可以改质量，但不能把 4000 字缩到 1200 字

**3. ReaderReview 增加长度维度**
- `reader-review.st` 新增 `length` 维度：章节是否达到预期篇幅
- 如果长度 < 2000 字，评分自动降分

**4. WritingPreferences 参数化**
- 新增 `minChapterLength`（默认 2000）字段，作者可调

### 修改文件

| 文件 | 改动 |
|------|------|
| `ChapterWriterAgent.java` | MIN 阈值 500→2000；从 prefs 读取 |
| `NovelOrchestrator.java` | 重写长度保护：`newContent.length() >= original * 0.7` |
| `ReaderReviewAgent.java` | 增加 length 维度评分 |
| `reader-review.st` | 新增篇幅评价维度 |
| `WritingPreferences.java` | +`minChapterLength` 字段 |
| `preferences-chat.st` | 文档化 |

## p9-2: 伏笔回收闭环 — ForeshadowingResolutionGate

### 根因
- `NovelOrchestrator.java:749,818` FINAL 转换无完整性检查
- `checkForeshadowingResolution()` 关键词+13词匹配，实际 0% 命中率
- `chekhovAudit()` 只记 MEDIUM issue，不阻塞
- `Foreshadowing` 无 deadline 字段
- `PlotterAgent` 不规划回收章节

### 方案

**1. FINAL 完整性门禁**
- 在 `runWritingLoop()` 和 `startNextVolumeOrFinish()` 的 FINAL 转换前：
  - 查询未回收伏笔 `findUnresolvedForeshadowings()`
  - 如果有重要伏笔（标记为 HIGH 优先级）未回收，**不转 FINAL**
  - 改为注入"回收指令"到下章上下文，继续写回收章

**2. LLM 驱动的伏笔回收检测**
- 替换 `checkForeshadowingResolution()` 的关键词匹配
- 新增 `ForeshadowingResolutionDetector`：每章写后用 LLM 判断"本章是否回收了某个未回收伏笔"
- 输入：章节正文 + 未回收伏笔列表
- 输出：哪些伏笔在本章被回收

**3. 大纲层伏笔规划**
- `plotting.st` 新增指令：每个伏笔必须指定预计回收章节
- `ChapterSynopsis` 新增 `foreshadowingsToResolve` 字段
- 写章时注入：本章必须回收的伏笔列表

**4. ChekhovAudit 升级**
- 未回收伏笔 > 5 条时，issue 级别从 MEDIUM → HIGH
- HIGH 会触发重写路径

### 修改文件

| 文件 | 改动 |
|------|------|
| `NovelOrchestrator.java` | FINAL 门禁 + LLM 回收检测替换关键词匹配 |
| `agent/ForeshadowingResolutionDetector.java` | **新建**。LLM 判断伏笔回收 |
| `prompts/foreshadowing-resolve-check.st` | **新建** |
| `domain/ChapterSynopsis.java` | +`foreshadowingsToResolve` 字段 |
| `domain/Foreshadowing.java` | +`priority` 字段（HIGH/MEDIUM/LOW） |
| `prompts/plotting.st` | 新增伏笔回收规划指令 |
| `AgentConfig.java` | 注册新 Agent bean |

## p9-3: 角色群像 + 情感深度 — CharacterEnsemble

### 根因
- `NovelOrchestrator.java:134-153` conceiving 只设计 1 个主角
- `character-design.st` 无性别/年龄/情感角色字段
- `GenreRuleProvider` HISTORICAL 规则全偏政治，无情感/人物多样性
- `chapter-writing.st` 无情感场景/关系发展指令

### 方案

**1. 角色群像设计**
- `runConceiving()` 中主角设计后，增加"配角群像设计"步骤：
  - 调用 CharacterDesignerAgent 设计 2-3 个关键配角
  - 至少包含 1 个女性角色 + 1 个对手/反派
  - 传入主角信息 + 世界观摘要作为上下文

**2. 角色模板增强**
- `character-design.st` 新增字段：
  - 【性别】男/女
  - 【年龄】
  - 【与主角的关系】盟友/对手/恋人/师徒/血亲
  - 【情感功能】该角色在故事中的情感作用

**3. 题材规则增强**
- `GenreRuleProvider` HISTORICAL 规则增加：
  - "至少 1 个有深度的女性角色"
  - "每卷至少 1 个情感场景（非纯政治博弈）"
  - climax 建议增加 EMOTIONAL_REVERSAL

**4. 章节写作增强**
- `chapter-writing.st` 新增：
  - "每章至少 1 个角色互动的情感时刻（非纯信息交换）"
  - "角色之间的对话应展现关系张力，不只是传递信息"

### 修改文件

| 文件 | 改动 |
|------|------|
| `NovelOrchestrator.java` | conceiving 增加配角群像设计步骤 |
| `character-design.st` | +性别/年龄/关系/情感功能字段 |
| `GenreRuleProvider.java` | HISTORICAL 规则增加情感+多样性 |
| `chapter-writing.st` | +情感场景/关系发展指令 |
| `CharacterDesignerAgent.java` | design() 支持群像上下文（已有 characters 列表参数） |
