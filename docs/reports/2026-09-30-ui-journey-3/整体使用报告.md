## 缺陷与问题清单

### F-1（P1）章级「让 Agent 修改」预览轮询 404，功能不可用
- 现象：弹窗内点「生成预览」→ 约数秒后「预览生成失败：No static resource api/projects/{id}/long-tasks/agent-revision-preview-{uuid}」
- 根因：前端 `getLongTask` 统一请求 `GET /api/projects/{id}/long-tasks/{jobId}`（client.ts:663），而后端该资源仅存在于
  - `RevisionController`：`/api/projects/{id}/revisions/long-tasks/{jobId}`
  - `ReviewDecisionController`：`/api/projects/{id}/chapters/{chapterIndex}/long-tasks/{jobId}`
- 影响：章节/段落级 Agent 修订（预览-确认流，p37/NCS-086/094 特性）在 UI 上完全不可用；对话框无同步回退
- 建议：按任务类型拼接正确的轮询路径，或后端提供统一 `/api/projects/{id}/long-tasks/{jobId}` 聚合查询
- 备注：**上一轮架构深化测试未覆盖此入口**（其报告仅测了 recheck-async，走的是 chapters 路径）

### F-2（P2）框架审阅「修改意见」对既有人物卡无修改路径
- 现象：修改意见明确要求"合并殷素更/裴无秤、骨更去记账腔、体型差异"，修订执行后原 8 卡文本逐字未变；仅新增大纲新配角 6 卡（新卡的"作者要求"上下文里带了我的意见）
- 根因：`reviseInitialSetup` 的人物层同步（NCS-090）按设计只做"补大纲新配角卡+点名零出场卡"，`instructions` 仅作意图门控与新卡上下文，不作用于既有卡
- 影响：对话框文案（"如：…补充人物心理"）让作者以为人物反馈会被执行；实际只有世界观被重写
- 建议：a) 意见分类路由（人物类→逐卡 CharacterDesigner 修订）；b) 或在对话框明示"人物卡请到卡片级『让 Agent 修改』"；c) 卡片级修订入口修复 F-1 后可承接此需求
- 关联：上轮 A-1（人物反馈静默丢弃）的修复（NCS-090）解决了"补卡"，未解决"改卡"

### F-3（P1→已现场缓解，环境类）默认模型路由长调用不可用
- 现象：`ui-default (glm-5.3-flash)` 章写 2/2 次 EMPTY_RESPONSE（122s/125s 确定性截断）→ 熔断；GENERAL 3 次 EMPTY_RESPONSE（94-171s）
- 影响：新建项目若不改路由，第 1 章必卡（本旅程被迫排障）；GENERAL 失败导致修订后 POST_PROCESS 停摆（POST_PROCESS_STAGE_UNKNOWN，无自动重试）
- 建议：a) POST_PROCESS 对 GENERAL 失败应有退避重试；b) 新项目向导可在选择模型时提示"长文本任务建议选择已验证模型"；c) 诊断页可标红连续 EMPTY_RESPONSE 的路由
- 正面：**模型库+任务路由 UI 是本旅程的救生索**——两处路由切换即时生效，无需重启，真实读者可自助恢复

### F-4（P3）「批准当前稿」后任务不自动恢复，且错误信息过期残留
- 现象：批准 v3 后 writing-tasks 仍 PAUSED 且 errorMessage 显示旧的"请先处理待审核内容"；需再点「继续协作」才恢复
- 建议：批准后自动恢复运行（或在按钮文案标明"批准后需手动继续"）；错误信息随状态清理

### F-5（P3）「引用素材」开关 UI 偶发不生效
- 现象：真实点击/原生 click 均无法持久开启，其余开关正常；API 直调正常 → 前端小尺寸 Switch 命中/时序问题待复核

### A-3 复现确认（P2，上轮遗留）
- checkpoint 修订路径（reviseCheckpointChapter）的 LLM_CALL 事件仍不带 projectId，事件流无法归属项目（本次 16:35 CHAPTER_WRITING 调用在项目过滤下不可见，实为修订调用）

### F-6（P1）后处理「记忆摘要」阶段 NETWORK 重试无退出，卡死整个项目 50 分钟
- 现象：第 3 章通过质检与质量评审（7/10 通过）后，MEMORY_SUMMARY 阶段（路由 qwen-flash-check）长调用持续 NETWORK 失败——事件显示单次重试累计 2,942,776ms（≈49 分钟）后仍 CHAPTER_FAILED，期间整个项目无法进入下一步（修改意见提交被"上一章的 Agent 仍在收尾质量检查"守卫正确拒绝）
- 根因链：环境层面是本机代理 127.0.0.1:9098 掐 >4min 长连接（服务进程继承 http_proxy，load-env.sh）；产品层面是**重试无 max-attempt/无明确失败终态**——阶段失败无限退避重试，用户无感知也无出口
- 处置：重启实例剥离代理变量（LLM 直连上游）后立即恢复
- 建议：a) 后处理各阶段加最大重试次数与显式 FAILED 状态（UI 可见+可手动重跑该阶段）；b) 大上下文阶段（记忆摘要/全书快照）考虑流式或分段以缩短单请求时长；c) load-env.sh 默认为 LLM 域名设置 no_proxy

### F-7（P2）JVM 重启后「审阅修订中」同步锁残留
- 现象：重启后横幅仍显示"审阅修订中 · 已 18 分钟"（旧 JVM 的操作锁持久化残留，工作线程已死），阻止新的修改操作
- 处置：UI 提供「取消该操作」逃生口，点击后立即释放项目工作权 ✅
- 建议：启动时对超时（如 >15min 无心跳）的同步操作锁自动过期

### 第 2-3 章循环记录（每章审阅实测）

- **第 2 章《更牌验籍》**（3,735 字 v2）：三类审阅面板给出 1 条真连续性问题（罗铜眼将未持剑的陈九斤登记为"罪剑民"，与《禁剑律》定义冲突——**检查器抓得准**）+3 条桥段重复误报（仅写 2 章即报"最近 8 章内已使用"，见 O-4）。读者以「问题裁决」处置：真问题记"创作例外"（罗铜眼滥用法籍构陷属人物动机），误报记"误报"，理由入台账（review_dispositions 可审计）；屏障视图「确认已复核并批准」放行
- **第 3 章《采铁账》**（v2 2,641 字 → QualityCouncil 打回 → v3 3,148 字）：consistency-guard 对 v3 报 3 条严重 HIGH——伏笔"无名之人"被错收为阿铃编号、沈青迟铜漏表能力越界×2。**读者走检查点「修改意见重写」提交针对性修复指令**（进行中）
- 观察到的正确机制：单章失败不跳章（退避重试→暂停）、重写仲裁（NCS-100）、质量评审打分（7/10）、过期检查不阻断（v2 的"过期"标注）、处置台账不可撤销提示

### F-8（P3）质量评价页的问题计数混淆现版/过期版本
- 现象：「必须处理 24」将 ch2 已裁决项、ch3 v2 已过期项（标"过期"）与 ch3 v3 现行项混计；而章节卡上"未解决 HIGH 问题：3"是正确口径
- 建议：分层计数（现行 X 条 / 过期 Y 条 / 已裁决 Z 条），过期项默认折叠

### F-9（P2）HIGH 阻塞时的处置入口与批准反馈体验
- 现象：第 3 章 v3 有 9 条现行 HIGH（伏笔回收错误 1 + 能力越界 5 + 凭空证据 3，检查器抓取细致、质量高），批准被拒后提示"批准未生效：当前稿存在阻塞项…"列出全部问题，但**当前位置不提供逐条裁决按钮**；"作为创作例外保留"按钮在三类分层区偶发不可定位（本会话多次尝试失败）
- 读者实际被迫改走 API（POST /dispositions + /review-decisions），行为与 UI 同源、台账一致
- 另发现：**DEFER（暂挂）不算"有效裁决"、不放行批准**——文案"批准门禁按台账豁免误报与创作例外"与三类语义一致，但与"暂挂=推迟处理"的直觉相悖（暂挂的问题仍阻断本章）
- 建议：批准被拒的内联提示直接附裁决入口；或在未修复通道（F-1）期间允许"带簿放行"（approve-with-defer）

### 第 3 章排障与裁决全程（旅程中最重的一次协作）

1. v2 2,641字 → QualityCouncil 打分 7/10 但打回重写 → v3 3,148字
2. v3 被 consistency-guard 判 9 条现行 HIGH（伏笔"无名之人"被错收为阿铃编号；沈青迟铜漏表被写成"认名魂铃/计数魂缺"；阿铃左耳失聪设定被违反、凭空引用律条；关键证据碑灰/刮碑无获取场景）——**检查体系对能力边界与证据链的把控是本轮最大惊喜**

### O-4（新增观察）桥段重复检测器的窗口口径
- 第 2 章即报"最近 8 章内已使用过「公堂对峙」等 3 个桥段"，实际此前仅 1 章正文——疑似与章纲桥段库（每章 synopsis 的 beats）比对而非已写正文；判定等级（中等）也直接进入"必须处理"，与arch深化报告所述"循环重复 HIGH 屏障"同源
- 建议：桥段重复检测只对已写正文生效；或对章节序号 < 窗口宽度时自动降级为"文学建议"

### O-5 卷边界无前台仪式感（对照上轮 NCS-082）
- 卷 1 第 6 章批准后直接进入第 7 章（WRITING），未出现 VOLUME_DONE 检查点/卷快照提示——大纲一次规划三卷时卷边界可能只在状态机内部流转。对读者而言"第一卷完"是重要的确认点，建议在卷末检查点 UI 上显式呈现卷小结（已完成伏笔/章数/字数）
- 第 4-6 章循环（API 批准 + 每章审阅）：ch4 1 HIGH（伏笔，EXCEPTION）、ch5 仲裁重写 v2→v3 后 0 HIGH、ch6 0 HIGH——**随上下文稳定，质量门禁通过率显著上升**；单章端到端耗时（写+检+审）约 25-45 分钟

### F-10（P2）读者评审/长任务撞 provider 冷却即失败且无重试
- 现象：reader-review 长任务恰逢 qwen-flash-general 熔断冷却（10s 窗口），LongTaskService 直接判失败（服务日志"长任务失败"），前端无任务入口可见（受 F-1 影响），只能再等下一暂停窗口重提
- 建议：长任务提交时若 provider 冷却，延迟入队而非立即失败；或冷却结束时自动重跑

## 结论

系统在**内容生产质量**上表现突出：世界观/大纲与构思强咬合，检查器（一致性守卫的能力越界/凭空证据/伏笔回收检测、时代用语穿帮、说明文密度）达到了真人编辑级的细致度，质量委员会与仲裁重写确实在抬升稿件质量（ch5-9 HIGH 持续走低），三类分层审阅与裁决台账的治理设计诚实可审计。作者协作的每个粒度（全书框架/单章/单段/偏好）都有入口。
