## 过程问题完整清单

### 问题 #1：篇幅无法自定义 20 章（中等）

- 创建表单篇幅仅预设 24/100/200/400 章，Select 不支持自由输入；创建后（写作偏好/项目设置）也没有任何修改目标章数的入口（targetChapters 仅创建表单可见）。
- 体验影响：想写 20 章的作者只能选 24 章再手动删章，或写满 24 章。
- 应对：以 24 章创建，人工在大纲删 4 章（顺带体验大纲编辑）。

## 问题清单（续）

### 问题 #2：活动写作期设定类编辑被拒且文案不引导（低-中）

- Agent 写作期间修改人物卡点"保存人物"→ 409「已有进行中的写作任务，请先暂停或取消」。限制本身合理（防并发写），但错误文案没有提示"先接手编辑"（p32-12 只覆盖了章节正文 mutation 的提示），作者会困惑。
- 同类：大纲页"保存未写大纲"同样被拒（「请先暂停写作再修改设定」）。

### 问题 #3：大纲删除章节无二次确认（低）

- 删除卷内章节点击即删（前端即时生效），无确认弹窗；误点即丢（有"保存未写大纲"兜底，未保存可刷新找回，但 UI 未提示这一差别）。

### 问题 #4：删章与保存被活动任务拒绝——状态不一致（中）

- 活动写作期：删除章节在前端即时生效（列表少了 4 章），但"保存未写大纲"报错被拒。作者视角"明明删掉了却保存失败"，刷新后章节又回来——同一页面内两种编辑的冲突语义不一致。

### 问题 #5：人审裁决不随作者改稿重估，且 UI 不提示问题针对旧版（中）

- 第 1 章 v3 被一致性门禁标记 NEEDS_MANUAL_REVIEW（17 条 HIGH）。作者改成 v4 后，质量报告正确地把 17 条全部标记 stale（p32-05 生效、可见），但：①章节状态仍 NEEDS_MANUAL_REVIEW，需作者手动"已处理"放行——合理，但 ②UI 报告顶部不显示"以下问题针对 v2/v3，当前 v4 未复检"的汇总提示，作者容易把 17 条 HIGH 误读为当前稿的问题；③高分（A/8）与 17 条 HIGH 并列展示，语义未分区（报告 #3 的"文学评分/事实风险/流程放行分开显示"建议仍未实现）。

### 问题 #6：质量报告问题与当前正文对应性差，作者核实成本高（中-高）

- 第 2 章 B/7、20 条问题（14 stale/6 当前）。逐条核对当前稿（v3）：多条"当前 HIGH"在正文中已不存在或本就自洽——如「汇款单三天前/邮戳今天冲突」：正文原句"三天前，外地预付三十……今天扣押"语义自洽（汇款日≠扣押日），检测器误读；「你冒充我」「第三张入殓登记卡」「邮戳」等引用段落在 v3 中不存在（疑似针对 v2 的残留或检测幻觉）。
- 影响：作者无法信任问题清单，逐条回原文核实成本高于自己通读——p32-05 的 stale 标记有效但 stale/当前划分也不准（14/20 vs 实际更少）。
- 好的一面：B/7 分与"对话过密、节奏快"的文学判断准确；HIGH 中确实存在真问题（如"铅笔字/墨迹未干"类物理矛盾在 v2 中真实存在）。

### 问题 #7：人审停点时 UI 不自动定位待审章节（低-中）

- 写作停在"第 2 章待人审"，但章节列表仍选中第 1 章；作者点卡片上的"已处理"按钮报错「仅 NEEDS_MANUAL_REVIEW 状态的章节可处理人工复核」——错误指向当前选中章而非待审章。应自动滚动/选中待人审章节，或按钮只在待审章显示。

### 问题 #8：单章全链耗时 40-60 分钟，20 章约需 15 小时机器时间（高）

- 实测 ch1-ch3：每章「正文生成 + 连续性/读者/一致性/风格/桥段/收割/伏笔检测」后处理链 10-20 次 LLM 调用（单次 1-5 分钟），单章全链 40-60 分钟。仅主动接手模式下作者绝大多数时间在等待；若无自动过审，20 章需跨天。
- 关联：ch3 完成（v3, 4546字, NEEDS_MANUAL_REVIEW）。节奏比之前体验（ch2 约 30 分钟）更慢，与章节长度和门禁数量相关。

### 问题 #9：编辑器允许零修改保存，产生垃圾版本（低）

- 正文编辑弹窗中未做任何修改（锚点替换失败、内容原样）点"保存正文"→ 成功保存为 v4：版本 +1、生成一条与 v3 内容完全相同的版本快照。应禁用保存或提示"无修改"；至少快照层可跳过无差异保存。

### 问题 #10：报告"当前 HIGH"与最新正文脱节比例高（与 #6 合并观察）

- ch3 报告两条核心 HIGH（登记卡第五/第四张矛盾、口型先七后我）在 v3 正文中均不存在对应文本——疑似针对 v2。stale 划分（5/12）与实际不符，作者逐条核实的负担仍然重。

### 问题 #11：段落级 Agent 修订的默认定位异常（中）

- 从正文打开「让 Agent 修改」，对话框目标显示"第4章 · 第915段"——本章实际不到 100 段。915 是非法段落索引，若直接生成预览/应用大概率失败（此前 UI 验证亦有段落应用报失败现象）。疑似段落 index 取自错误的 DOM 遍历。作者需要自行弄清"目标"语义，无法直接选"整章"。

### 问题 #12：重写此章后版本审计链断裂（高）

- ch4「重写此章」提交意见后：内容确实按意见重写（发夹铺垫落实、5470→7066 字），但 versions 快照仅剩 [(2,REWRITE)]，当前 version=3——**重写前的 v3 内容没有任何快照**，无法回退到重写前；版本号也未按 CAS 语义推进到 v4。违反「变更前不可变快照」的保障。疑为重写触发的后处理链中仍有无快照的 saveChapter 覆盖（p32-02 改造了 3 处，仍有漏网路径）。
- 影响：作者对自动重写结果的"后悔药"缺失——不满意也无法回到重写前。

### 问题 #13：重写修改意见的落实不完整且无核对提示（低-中）

- 提交了 3 点修改意见，结果仅"发夹铺垫"落实；"求证台词改造"未体现，且 UI 不展示意见与结果的对照，作者需自行 diff 全文核对。

### 问题 #14：复检问题跨轮累积（中）

- ch4 重写后复检多轮，issue 从 19 条涨至 23 条：每轮复检对同一能力越界/凭空证据各追加新行（p32-09 仅去重了伏笔悬置提醒，一致性/能力类复检仍逐轮累积）。报告顶部无去重视图，作者看到的 23 条中大量语义重复。

### 体验观察（非问题）：定向重写意见可落实

- ch4 提交三点修改意见的整章重写：显式铺垫类意见落实（发夹提前出现），但行为改造类意见（主角先求证再推断）未落实——LLM 对"台词模式改造"类意见的遵循弱于"新增铺垫"类。意见与结果无对照展示（问题 #13）。

### 问题 #15：伏笔埋设门槛过低，台账爆炸（高）

- 5 章累积 97 条伏笔（70 未回收），单章新增 15-20 条；大量条目是细节级信息（「报警信寄出时间差」「口型被摆成七」），且多数无 expectedResolveChapter（预计回收章为空）。真典已达 87 条。
- 影响：台账失去"叙事承诺"的筛选意义；ContextAssembler cap 12 裁剪后作者难以分辨真正的主线伏笔；回收判定（p32-08 已收紧）在 70 条未回收里做匹配，误报率会进一步放大。
- 关联报告 #4：埋设滥 + 回收误判双向夹击，伏笔系统的信噪比是当前长程记忆的最大短板。

### 问题 #16：跨章铺垫识别弱（低-中）

- ch5 报告 HIGH「发夹齿无铺垫」——实际 ch4 重写已按作者意见加入发夹铺垫。检测器对本章外的前文细节（真典摘要窗口外）视而不见，跨章呼应被误报为凭空证据。

### 问题 #18：人审停点行为不一致，NEEDS_MANUAL_REVIEW 常无法阻断后续写作（高，二次强化）

- ch2/3/5/7/8：标记后写作循环暂停交还（ch7 交还滞后 30+ 分钟）；**ch10：标记后系统直接继续写下一章**——作者点"已处理"被 mutation 门拒绝（busy），待审章持续积压，作者完全失去介入点。
- 根因方向：collaborationBlocker 只检查 currentChapterIndex 指向的章节状态，而索引在门禁标记前已推进；stop 与否取决于后处理收尾时序。人审停点因此不可靠——这是"人机协作"承诺的核心缺陷。
- 实操影响：作者只能等偶发 idle 窗口批量放行待审章（本次 ch8 即积压 45 分钟后才放行）。
